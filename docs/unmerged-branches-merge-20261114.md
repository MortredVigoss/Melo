# 未并入 master 的 12 个本地分支：核对与合并记录 · 2026-11-14

用户要求："检查一下这些没有提交的，全部都合并，然后 debug 一下，在 GitHub 上弄成最新最全版本。"对象是本机 `git branch --no-merged master` 列出的 12 个分支。远端分支此前已全部在 master 里。

## 1. 结论

- 12 个分支全部并入 master，`git branch --no-merged master` 为空。
- 其中 11 个分支的内容 master 早已有了（原样、评审后的版本，或被后来的实现取代）。它们用"只记录、不改文件"的方式合并：分支的提交进入 master 的历史，文件一个不变。
- 只有 `codex/reply-latency-20261109` 带着 master 没有的功能。它和 master 在 11-10 之后各自做了一遍回复延迟优化，两边有重叠。逐项对照后，master 已经用自己的方式解决的保留 master 的做法；master 没有的带进来，并按 master 现在的代码改写。详见第 4 节。
- 一项功能没有启用：iPhone 上"两个只读成员同时运行"。原因和需要用户决定的事在第 7 节。

## 2. 核对方法

对每个分支，取它离开 master 之后改过的每一个文件，查"这个文件在分支末端的确切内容，是否曾经是 master 历史里的某个版本"（按 Git 对象号比对，脚本 `.tmp/merge-unmerged-20261114/classify.py`，不入库）。结果分四类：与 master 现在相同；曾是 master 的某个版本（说明内容进过 master，之后 master 又改了）；master 有这个路径但从未有过这个确切版本；master 从未有过这个路径。后两类逐个打开看。

直接 `git merge` 不能代替这一步：一个文件如果分支加过、master 后来有意删掉，三方合并会把它悄悄加回来；一段代码如果分支改过、master 后来改回原样，合并也会悄悄恢复分支的改法。所以内容已在 master 的分支不做内容合并。

推送前还检查了将要随合并进入远端的 590 个 Git 对象：没有形似密钥、令牌或私钥的内容，超过 1 MB 的只有手机字符串表和场景包这两个生成文件的旧版本。

### 4.3 没有带进来的：会带来退步或没有收益证据

- **网页先用普通 HTTP 读一次（静态网页不走浏览器内核）。** 这条路径只在正文区域里没有脚本时才成立，多数网页会回退到浏览器内核，等于每次读网页多发一次请求、多等最多 2 秒。它取到的文字也和浏览器内核不同（包含隐藏元素、不保留换行）。分支自己的实测里检索类任务是略慢的。master 的读网页路径 11-10 用真实任务量过，这里不加一个没有量过收益的前置步骤。连带没有带入它的模拟器验证入口。
- **iPhone 两个只读成员同时运行。** 见第 7 节。

## 5. 合并时发现并修掉的问题

### 5.1 分支的流式解码器（都在并入前修掉，各有测试）

1. 不带参数的工具调用在 Anthropic 流式下会让整个回复失败：这类调用的参数流是空的，分支把空字符串当 JSON 解析。
2. 服务不发调用 id 时工具调用被拒。master 11-10 刚为非流式修过同一个问题（`identifiedToolCalls`），分支的解码器在流式下把它带了回来。
3. 流里的续片如果带 `"name": null`，整段参数片段被丢掉（把字典强转成"全是字符串"失败），拼出来的参数是坏的。
4. 服务发完结束原因后直接断开、不发 `[DONE]` 时被判为断流。桌面端的读取器一直把"已收到结束原因"当作完成。
5. 分支的测试用"首段文字在 0.25 秒内到达"判断草稿先于回复结束，门禁并行跑测试时会随机失败。改成由测试控制：服务端等测试确认看到草稿后才发结束帧。

解码器现在与桌面端 `src/providers/streams.js`、`anthropic.js` 的规则一致。

### 5.2 "相同答案不重复核对"在 iPhone 上从不生效

比较用的是把核对输入转成文本后逐字比较。iPhone 把目标状态存在字典里，字典没有键顺序，状态在 Swift 和共享核心之间往返一次，同样的内容就变成了不同的文本，于是每次都判为"有变化"、照常请求核对。分支在 iPhone 上没有覆盖这条路径的测试，所以没有发现。现在比较前先按键排序，缺失和 null 也视为相同；共享核心和 iPhone 两边都有测试。

### 5.3 其他

- 分支在合并冲突之外自动合进来的几处会改掉 master 的行为，逐个还原：桌面派单循环的收尾、成员阶段编号的改写、`NetworkTests` 里一条按分支编号规则写的断言。
- 被打回的核对输入最多 12.8 万字符，会跟着目标状态走。手机和 Android 写执行追踪时把这一项去掉，回执快照里也不带它。

## 7. 没有做、需要用户决定

**iPhone 两个只读成员同时运行**（分支的第四项）。没有启用，分支里的实现保留在 Git 历史中（`4b46fa9e`）。原因有三条：

1. 它按 11-09 的预算规则给成员分配额度。master 11-10 修过这条规则（手机原来没有扣除收尾预留，晚启动的成员会用掉留给主 Agent 写答案的额度），分支的实现会把这个问题带回来。
2. 它让每个并行成员各跑一遍完整的带核对的循环。master 11-10 为了延迟去掉了只读成员自己的完成核对。
3. 它在三端共用的派单提示词里告诉主 Agent"可以一次派两个"。Android 一次只接受一个派单，多了会整批拒绝，每次白费一轮。

要做这件事，需要在 master 现在的成员机制上重新设计（预算怎么对半分、暂停后怎么续、Android 是否同步支持），是一项独立的工作，不是合并能完成的。
