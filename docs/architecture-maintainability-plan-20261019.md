## 3. 目标结构与接口

### 3.1 业务操作与页面查询分开

沿用现有 `src/domain`、`src/services`、`src/state`、`src/providers`、`src/http`，先收紧职责与导出接口，避免全仓搬目录。

```text
桌面页面 / CLI / HTTP / 同步适配器
              ↓
业务操作：修改项目、保存 Agent、发送聊天
              ↓
领域规则 + 明确的存储/模型/工具接口
              ↓
现有事务存储、供应商适配器、设备实现

桌面页面 ← 页面查询服务 ← 已提交的领域数据
iPhone 页面 ← 对应的本机业务服务 ← Swift 存储与设备实现
              ↕
共享 schema、错误/事件约定、双端共同测试样例
```

示例：项目更新操作只返回已提交结果，如 `{project, revision, changedIds}`。这些字段由实际提交生成。兼容 HTTP 适配器按旧客户端需要再组装 bootstrap，旧 URL/响应先保留；新页面逐步改为读取项目、Agent、聊天等有限查询。

这样先建立接口，再优化查询成本。保留旧客户端兼容路径期间，部分请求仍有整体组装开销，应据实报告。保存成功而后续页面刷新失败的错误语义，单独设计和测试，不能在“纯搬代码”中悄悄修改。

业务模块最终不再导入 `services/desktop/bootstrap.js`；已迁移模块禁止通过兼容入口绕回。模块公开入口只导出本模块能力，避免再造一个加载全产品的总出口。

### 3.2 桌面 UI 按功能封装状态、渲染与动作

建议逐步建立 `desktop-ui/features/{projects,agents,chat,knowledge,settings}/`。每个功能管理自己的状态、动作、渲染与请求，应用入口保留导航、组合和顶层生命周期。以下是建议文件，当前尚不存在：

```text
features/agents/
  controller.js     页面动作与保存流程
  state.js          草稿、编辑/保存状态、局部选择
  view.js           页面展示
  api.js            有限请求接口
  agents.css        本功能样式
```

先试点“项目编辑/资料选择”，证明页面边界和旧 API 兼容；随后迁移最常改的 Agent 设置，再处理聊天。组件只接收所需数据和回调，不把整个 `uiState` 原样传入每个模块。

初次抽取保留现有 DOM/CSS 结构和动作语义；局部渲染是后续独立步骤。神经场景、编辑草稿、输入法组合、滚动、媒体预览、保存失败/取消都须通过回归后才能替换原保护逻辑。全局 CSS 逐区归属，抽样比对前后计算样式，避免全站重排。

### 3.3 聊天执行保持明确的几个阶段

继续使用现有 prepare → invoke-model → finalize 语义，抽出明确输入输出：准备本轮上下文、执行模型/工具续接、保存结果并调度后续工作。

- 准备阶段产出只读的本轮数据快照：聊天/Agent/项目身份、已解析的模型与工作区、允许能力、上下文证据和预算；运行句柄与数据分开管理。
- 执行阶段接收有限接口，例如模型调用、工具执行、事件记录；不接收整个应用容器或可变全状态。
- `requestScope` 继续在入口绑定 home、身份与取消信号；保持执行器拒绝缺失能力上下文、子任务权限交集、同聊天队列、超时与迟到结果处理。
- 供应商适配返回统一的文本、工具调用、用量与结束原因，保留 Codex / Responses / Chat Completions / Anthropic 的全部已支持行为及原始诊断信息。
- 图片与团队保留专有流程与可验证结果，通过明确入口接入编排；不把它们压成文字问答的简化分支。

`openai.js`、记忆库和搜索大文件在相应接口稳定后再按协议/职责拆分。图上入口的依赖闭包本就可能较大，目标是稳定接口与清楚的修改影响范围，不是人为把每个入口的依赖数字压到很小。

### 3.4 手机保留独立运行，ChatStore 逐步缩成界面协调层

优先抽出独立对象，而非只把同一类放进多个 extension 文件：

| 建议对象 | 责任 | 必须保持的行为 |
| --- | --- | --- |
| ConversationRepository | 聊天/草稿/偏好持久化与恢复 | 旧文件可读、写失败保留、原消息和图片引用不丢失 |
| TurnCoordinator | 主对话、团队、图片、补充、取消和预算 | 复用现有 AgentLoop；各聊天并发隔离，迟到结果不写入 |
| DeviceApprovalCoordinator | 审批队列与授权回执 | 超时/取消后不能迟到执行，下一轮可正常继续 |
| WorkspaceSyncCoordinator | 聊天/项目/Agent/记忆同步与冲突恢复 | 原同步令牌/协议兼容、tombstone、待恢复日志和提交顺序 |
| ExecutionRecordStore | 运行轨迹与任务回看 | 事件次序、用量、耗时、失败和重启恢复语义 |

`ChatStore` 初期保留原公开方法和 `@Published` 表面，内部转发给新对象，让现有 SwiftUI 页面继续工作。抽取过程保持 `MainActor`、任务所有权与取消链；不能为了拆分取消隔离规则。

JavaScript 与 Swift 各自执行平台逻辑，继续扩充已经存在的共享协议和夹具。补充“上下文选择结果、权限拒绝、团队交接、取消/错误结果”的成对测试，并明确手机设备工具与桌面文件/命令工具的合理差异。

### 3.5 领域数据先约束访问，后考虑物理存储

项目、Agent、聊天、资料、记忆分别定义所有权和有限读取/修改接口，服务不再随意修改整份 state 的其他领域。跨领域操作继续由现有事务协调器统一提交，不能拆成多份各自提交的数据库而丢掉原子性。

第一批保持 state/checkpoint 格式、主键、Keychain、账号配置、图片路径和同步版本。后续需要历史分页或项目聚合时，先建立读取接口，再做可备份、可重放的迁移；回滚方案必须处理升级后新增的数据，不能直接恢复旧快照丢掉后续聊天。

冷启动按需读聊天正文、聊天列表独立查询等性能工作放到此阶段，并先测当前冷启动、bootstrap 和内存基线。当前数据量与静态审计不足以决定要更换数据库或运行时。

## 4. 让修改更容易定位和验证

建立功能清单（建议 `architecture/modules.json`），记录模块公开入口、允许依赖、桌面/手机对应实现、共享契约、测试组、维护说明和隐式依赖。构建生成、路由注册、native bridge、读源码的测试都必须登记，不能只依赖静态 import 推断影响。

建议命令 `npm run scope -- <changed-files>` 输出：受影响功能、应核对的另一端、需要的测试/构建层级和原因。初期只报告，不减少现有检查；经试点验证的模块才允许缩小日常组。测试可按“模块回归 / 边界集成 / 全量发布”组织，发布仍跑全量；未知依赖、权限、存储迁移、同步协议、生成器变更继续保守扩大。

立即可规划的小修：将 `MELO_OVERVIEW.md`、`AGENTS.md` 和已确认只作说明的文档登记到文档规则；不能把所有 Markdown 都当成非运行时文件，因为技能/人设文件可能被运行时读取。验收要求纯文档检查只处理链接与规则，不启动浏览器、Swift 或安装。

手机测试继续保留现有编译缓存。模块边界稳定后，再缩小 `ios/scripts/test.py` 中公共 `shared` 输入集合；不以缓存命中或编译通过代替实际运行，也不删除生产入口的模拟器测试。

总览建议收敛为“当前事实 + 功能索引 + 最新交接入口”；阶段过程转入已有 `docs/handoffs/` 和专项记录。每项只保留一个现行状态及证据链接，历史保留日期/提交；固定测试数量改成引用带日期的回执。不是再维护一份手写全量文件清单。

## 6. 施工与验收约束

1. 每次只迁移一个完整功能路径；先按 CLAUDE.md 保留函数体搬迁，再单独提交接口/行为改动，机械移动与语义变化分开审读。允许必要的 import/export 接线，不借机简化实现。
2. 旧入口逐步转发到新模块，新模块禁止反向依赖旧入口。建立存量例外清单并逐批减少；不是一次全仓改路径。
3. 新接口使用 schema/JSDoc/明确 Swift 类型，优先约束边界数据；保留未知旧字段所需的兼容策略。暂不开展全仓语言迁移。
4. 两端已对齐的取消、上下文、能力、记忆、团队和资料行为全部保留；每个相关模块附桌面/手机共同场景，设备特性明确单列。
5. 账号、聊天、图片、Agent、项目、同步令牌与设置不做破坏性清理。日常测试使用隔离 home；实体覆盖与真实服务验收另行记录。
6. 用“改动触及的业务模块、中央文件是否继续增长、单模块测试能否隔离运行、回归耗时”衡量成果。文件行数是提示，不设机械拆文件配额。
7. 收窄日常测试前先验证显式/隐式依赖映射；对相同试点同时跑新选组和全量检查做对照。通过后仍保留发布全量，不能把快速通过当成全部通过。
