# 多图修改、上传上限、视频读取、出图分辨率：方案（2026-10-16，Claude）

用户在 0.5.23 实机使用后提出四点，要求先出方案。本文只是方案，尚未改代码。

## 1. 传多张图只修第一张

**根因（两端都有）**
- 手机：所有图片放进同一个请求，提示词写明“编辑时第一张是底图”；接收端拿到第一张完成的图片就结束读取，所以最多只回一张。
- 电脑：第一张作为底图、其余作为参考；“生成 N 张”只是把同一张底图重复修改 N 次。

**方案**
- 两种意图分开：
  - **逐张修改**（默认）：两张及以上图片 + 修改要求，且没有“合成 / 拼 / 融合 / 把…放到… / 参考…风格 / 结合”这类说法时，每张图单独发一次修改，同时最多 2 张，进度显示“第 2/4 张”，每张结果与自己的原图配对（预览的“结果/原图”对照按对应关系）。一张失败不影响其他张。
  - **合成/参考**：明确要合成时保持现在的一次请求，但接收端允许返回多张。
- 单条消息上限从 4 张提到 8 张，发送前显示将调用几次。
- 判断规则写进两端共用的意图用例，手机和电脑一致。
- 验收：3 张图 + “都调亮一点” → 恰好 3 次修改请求（计数器），3 张结果各配原图；“把这三张合成一张海报” → 1 次请求；其中一张失败时其余照常保存。

## 2. 24 MB 上限

**现状**：手机单张选图 ≤24 MB、参考图合计 ≤24 MB、处理后 ≤24 MB；电脑界面附件 ≤20 MB、看图 ≤20 MB。原因是图片以 base64 整体放进一次请求（体积再增大约 1/3），手机内存也有压力。

**方案（不是简单放宽，而是不再让用户碰到）**
- 原图按原样保存在本机（单张导入上限提到 100 MB），发送时自动生成“传输副本”：最长边 4096（看图分析用 2048）、重新编码，通常 1–6 MB。模型拿到的是副本，原图不变、可随时导出。
- 发送前合计上限按副本计算（约 40 MB），超出时提示减少张数，而不是拒绝大图。
- 视频走单独通道（见第 3 点），不受图片上限约束。

## 3. 读视频

**现状**
- 电脑：**有，但只是部分能力**。上传视频后抽 5–8 张关键帧（宽 512 px）+ 语音转文字，单个视频上限 200 MB，整个提取限 15 秒。但界面附件上限是 20 MB，大于 20 MB 的视频根本传不上去；15 秒对长视频不够，帧太少也谈不上“学习”。模型看到的是“截图 + 文字稿”，不是视频本身。
- 手机：**没有**任何视频入口。

**方案**
- 电脑：
  - 视频附件上限提到 500 MB，改为文件流式上传（不再 base64 塞进 JSON）。
  - 提取改为后台任务并显示进度，不再受 15 秒限制；按镜头变化抽帧（最多约 24 帧、768 px），整段语音分段转写并带时间戳。
  - 产出一份“视频资料”（时间轴文字稿 + 每帧说明），可一键存进“知识”，之后任何 Agent 都能反复引用，这才是“学习”。
- 手机：
  - 从照片/文件选视频；10 分钟以内在本机抽帧（系统视频接口）和转写（系统语音识别，可本机离线），再按电脑同样的格式交给模型。
  - 更长的视频交给电脑处理，结果同步回手机。
- 边界：当前接入的模型接口不直接接收视频文件（实施前用真实账号复核一次），所以理解方式仍是“画面帧 + 文字稿”。

## 4. 出图分辨率（2K / 4K）

**现状**：电脑走 Codex 登录时根本不传尺寸；手机只在提示词里写一句“横幅/竖幅偏好”；走 API 连接时会传尺寸，但只有 1024 级别的三档。所以实际出图约 1K。

**模型能力（OpenAI 官方指南）**：任意尺寸均可，条件是两边都是 16 的倍数、长边小于 3840、长宽比不超过 3:1、总像素在 655,360–8,294,400 之间；2560×1440 以上属于实验性质，最接近 4K 的合法尺寸是 3824×2144。

**方案**
- 图片选项增加：标准（约 1K）/ 2K（横 2560×1440、竖 1440×2560、方 2048×2048）/ 4K 实验（横 3824×2144、竖 2144×3824、方 2880×2880），并注明更慢、更贵、4K 结果不稳定。
- API 连接：直接把尺寸传给接口。
- Codex 登录：先用你的账号实测一次图片工具是否接受尺寸参数。接受就传；不接受就如实提示“此连接最高约 1K，需 2K/4K 请切换到 API 连接”。不会用本机放大冒充 2K/4K。现有的“最长边 2048”本机处理另外标明是放大、不增加细节。
- 结果页显示实际返回的像素尺寸，与所选档位对照。

## 实施结果（2026-10-16，同日完成，分支 `claude/media-20261016`）

| 顺序 | 项目 | 结果 | 验证 |
| --- | --- | --- | --- |
| 1 | 多图逐张修改 | 两端完成。多张图 + 修改要求默认逐张；说“合成/拼/放到…里/参考”才合成。手机每张单独请求、两张同时，结果各配原图；电脑每张一个任务。单条上限 8 张。顺带修正“这几张”被当成提问、“拼/合成”不算修改要求两处。 | 共享用例 11 条两端同跑；电脑测试按宽度证明 3 张各修一次；模拟器真实发送路径：3 张 → 3 次请求、结果对应原图，合成 → 1 次。 |
| 2 | 2K / 4K | 两端尺寸选项：标准、2K、4K 实验（2816 方 / 3824×2144）。API 连接直接传尺寸；Codex 登录现在也传尺寸，若服务拒绝（HTTP 400）只重试一次默认尺寸并在回复里写明，不冒充。手机存储上限提到 64 MB 以容纳 4K 结果。电脑结果记录实际像素。 | 两端测试：接受时只发一次；拒绝时恰好重试一次且不带尺寸；其他错误不重试。**未用真实账号实测 Codex 是否接受 2K/4K。** |
| 3 | 解除 24 MB 体验上限 | 手机：选图上限 100 MB，保存 ≤4096 px 副本（照片存 JPEG，生成结果保持 PNG），发送时再按用途压缩（分析 2048、改图 4096），单次合计 40 MB。电脑：照片 100 MB，浏览器先画成 ≤4096 px 副本再发送；服务端看图遇到超 20 MB 自动缩小而不是报错。 | 手机测试 27 MB 原图通过且原文件不被改写；电脑测试大图缩到 ≤4096。 |
| 4 | 电脑视频 | 视频 ≤500 MB 以文件流上传到本机（不再转成文本塞进请求），播放支持拖动；只接受本机来源。上传的视频直接从磁盘处理，时限 4 分钟，按每 15 秒一帧取 5–24 帧、宽 768，记录时间点；视频卡片可“存为知识资料”。 | 测试：上传、超限不留残文件、路径越界拒绝、分段读取、120 秒视频 8 帧及时间点。真服务器实测：上传 → 分段播放 → 跨站上传被拒 → 带视频发消息成功抽帧。 |
| 5 | 手机视频 | 相册选视频（10 分钟内），在手机上抽帧（同电脑规则）并转写语音（优先本机识别），模型收到画面 + 文字稿，对话里只留一行摘要；可存入知识。超过 10 分钟提示改在电脑上发送。 | 测试：帧间隔与电脑一致、模型文本、知识格式；模拟器用真实 60 秒视频跑通抽帧 → 发送 → 存知识。 |

**与方案不同之处**
- 电脑多图逐张是依次执行（手机两张同时）。
- 视频抽帧按时间均匀取，没有做“按镜头变化”，因为均匀取帧才能给出准确的时间点。
- 超过 10 分钟的手机视频没有做“交给电脑处理再同步回手机”，改为提示在电脑上发送（结果可存入知识后在手机使用）。
- 长视频的文字稿仍受原有长度上限（约 8000 字）限制。

**未验证**：真实账号下 Codex 是否接受 2K/4K、视频画面与文字稿的真实回答质量、手机语音转写（模拟器上未授予语音权限，只验证了“未授权时只用画面”的路径）、实体机。

## 追加：手机多轮图片上下文（2026-10-17，用户实机反馈）

用户实机（0.5.23，尚未包含逐张修改）反馈：后续消息读不到之前的图、改“第二张”总返回第一张、第二三轮常“乱生成”。读代码确认三个根因：发给模型的历史只有文字，之前的图从不再发送；后续消息只会指向“最近一条带图的消息”（即第一张的结果）；没有识别成改图的后续消息带着图片工具却没附图，模型只能凭文字新画。

修复：对话图片编号（图1、图2…，结果标明由哪张修改而来）；历史里每条带图消息标注编号；“第二张 / 原图 / 这两张都 / 图2 / 它”解析到具体图片（第 N 张指最近一次上传的第 N 张，默认取它的最新结果，说“原图”取原图）；点名旧图的修改要求按改图处理，提到旧图的提问会把那几张图带上；模型说明里禁止“提到旧图但没附图时凭空生成”。修复过程中发现并修正：后续消息引用旧图时不应被当成新上传。

验证：Swift 用例覆盖上述指代；模拟器真实发送路径跑通“两张 + 都换成晴天 → 第二张再亮一点 → 第一张原图是什么天气”。未验证：真实模型的实际表现；电脑端的多轮图片指代本轮未改（电脑另有图片跟进逻辑），需要时再对齐。
