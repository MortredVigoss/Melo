# 主 Agent 的任务范围、结果计数与评估：三个候选方案

状态：2026-11-05 用户已选择 B，并授权实现、合并 master、推送和 Mac 覆盖安装。数字作为版本化初始策略实施，真实质量阈值仍需后续人工校准。实施与验收见 task-evaluation-b-implementation-20261105.md。活动 / 商品均为假设场景，不是当周实际推荐。已授权的 R1–R7 缺陷修复独立推进。

## 当前实现实际怎样计数

核对基准 afdcce1，缺陷修复分支基于 431912b。当前桌面内部路由最多 6 次分派，每个成员最多 6 个工具轮；只读成员最多 3 个并发。成员默认输入份额 120k，主 Agent 保留 60k。普通整轮初始 40 工具轮 / 200 次工具调用 / 400k 输入 token / 30 分钟；成员的独立轮不占主 Agent 的 40 轮，但调用和 token 会累计到父池。

主线现有策略还会按成员扩容，最多 +480k 输入 token / +160 工具调用 / +20 分钟；这是资源规则，不是“核实了多少个活动”。本批只修预算与真实截止时间不一致的问题，不擅自替用户改变扩容政策。iPhone / Android 仍是内联成员，不能把桌面的独立调度数字直接当作手机行为。新策略选择后必须统一共享计数、设置含义与两端 UI。

## 先统一含义

主 Agent 保留当前自定义 Agent 的身份；内部协调器负责范围、分派、审查与汇总，不要求用户再选一个“路由人设”。三个方案都区分以下账本：

- **资源账本**：请求、工具调用、时间、输入/输出 token 与费用。失败、重复、未找到也消耗资源，不能以“还没找到有效结果”为由无限执行。
- **候选账本**：发现 → 已读 → 满足必要条件 → 已核实 → 推荐 / 备选 / 排除。一个实体一个计数；十个网页讲同一场活动仍是一项。一个页面包含三场分别可核验的活动可以是三项。URL 数、搜索命中数、成员报告数都不是有效结果数。
- **需求账本**：原始目标、用户追加条件、明确必须满足项、默认偏好、未解决缺口。约束不允许靠高分抵消，例如“免费”不能被“很好玩”抵消。

有效活动至少核实：可区分的活动身份、本地日期/时间、地点、公开参与方式与支持这些事实的来源。小型 home party 和官方活动使用同样的资格判断；本人公开邀请、时间地点和参加方式可核实，就可计数，不因平台或规模排除。仅限私人邀请、只有历史截图、日期待定的内容不冒充可参加活动，只列为待确认线索。商品则核实具体型号/变体、硬性规格、适用地区、可比价格口径与在售状态；不同商家卖同型号一般计一个商品、多条报价。

已核实只表示读取证据支持这些字段，不宣称绝对真实。原帖可以是一手来源，搜索摘要不替代实际读取；事实冲突不能平均打分后消失。

## 三方案比较

| 方案 | 主 Agent 如何决定范围 | 推荐质量 / 成本 / 可解释性 | 综合建议分（设计判断，非实测） |
| --- | --- | --- | --- |
| A：场景模板与可调配额 | 按活动、商品、事实查询等选择模板，完成资格门槛与目标范围后收尾 | 稳定、便宜、易验收；跨场景和模糊任务较僵硬 | 8.0/10 |
| B：需求合同 + 自适应批次（推荐） | 先生成可检查的任务合同，按新有效结果和剩余缺口调整后续搜索 | 平衡灵活性、可控成本和解释；需要实体账本与停止策略 | 9.0/10 |
| C：多路探索 + 独立评审 | 多成员按渠道/角度并行，另一评审者比较盲审，主 Agent 仲裁 | 适合高价值复杂采购/研究；更慢、更贵，评审也可能一起误判 | 7.5/10，适合作为 B 的深度模式 |

### A：模板配额

活动的建议默认：先发现 10–15 个去重候选，核实 5–8 个，主推 3 个，另给 2–5 个标题和链接；不为填满数字推荐不合格活动。至少尝试 2 类来源、覆盖 3 类兴趣，实际不足时说明搜索范围与不足。商品：无数量要求时核实 6–10 款、重点比较 3 款；明确要求 20 款就以 20 为目标，初始候选可放到 30–50 款，并允许继续扩展。

资源软检查点建议为 2 分钟或 12 次工具调用，到点检查是否足够；整轮硬上限仍服从共享预算。停止：用户硬条件和数量达到；或预设搜索批次完成、可访问来源不足 / 资源触顶，给出部分结果。优点是低成本、规则清楚；缺点是模板多了又变成大量条件分支，也容易为了配额搜到没价值的项目。模板须保存在共享版本化配置，而非散落 JS / Swift / Kotlin 的数字。

### B：需求合同 + 自适应批次

协调器先生成 `TaskContract`，包含：要交付什么、时间/地点/地区、硬条件、偏好权重、计数单位、目标区间、输出数量、覆盖维度、可用来源与资源上限。用户明确条件优先；“本周末”按用户已知地区和时区解析，地理不明先用已授权上下文，确实无法确定才问。推断的偏好标为默认，不伪装成用户要求。对简单事实题不跑复杂评分。

建议数字与行为：

| 情形 | 第一批 | 继续策略 | 交付 |
| --- | --- | --- | --- |
| “墨尔本周末有什么活动” | 发现 8–12 个独立候选；核实其中高潜力项目 | 目标 5–10 个合格项目；每批追加最多 5 个候选，优先补缺类别/时间段/来源；不是最多只能找到 10 个 | 主推 3 个，说明适合谁、时间地点和参与成本；其余 2–5 个标题+链接。标题所述活动也需符合基本日期地点条件 |
| “找符合这些条件的 20 个商品” | 发现约 30 个候选，按必要规格和地区逐项筛选 | 目标就是 20 个合格商品；每批补 5–10 个，不能用默认活动配额停止；找不足时返回实际数量和缺口 | 20 个可核验条目；如用户要推荐，再从中选 3 个重点 |
| “帮我选一个合适的耳机” | 6–10 个候选，先推断或澄清决定性预算/用途 | 核实 4–8 个，重点补足能改变前三排名的证据 | 1 个首选、2 个备选及取舍 |
| 单一事实 / 计算 / 操作 | 不设候选配额 | 事实达到所需证据；计算校验输入/单位；操作以最终状态回执为准 | 直接回答，不强行凑项目数 |

资源建议先沿用现有整轮硬预算 30 分钟 / 200 工具 / 400k 输入 token，用户明确设置更小值则服从；深度配置单独明示。正常模糊推荐设**软检查点**为 3 分钟或 20 次工具调用，先评估是否已足够，不是自动终止或自动涨预算。内部成员首批建议最多 4 个工具轮，需要补缺时每次申请 2 轮，默认每个成员累计最多 12 轮；所有申请都从整轮已有资源池分配，不刷新已花额度。每批最多规划 8 次工具调用、90 秒的工作片段，遇到长页面可以结转；具体值进统一契约并通过真实耗时校准。收尾/核验额度在开始时保留，不因多派成员无条件 +120k。成员只得到总池的份额，不按“多生一个成员就多给钱”扩容。用户明确要 20 个时，这些预算仍然有效，触顶就部分交付而不是谎称完成。

停止判定分两层：

1. **硬门槛**由宿主验证可计算部分：日期/地区/价格等结构化条件、实体去重、引用对应实际读取、冲突标记、明确数量、执行副作用回执。语义上是否真正支持某个结论仍须对照来源内容核对；仅有合法证据 ID 不等于内容蕴含结论。无法可靠判定的字段保持待核实。未过不能 completed；评分不能覆盖失败门槛。
2. **信息是否足够**由协调器建议、宿主验证：通常先达到建议有效数、主要推荐均有充分依据、重要偏好/类别覆盖，再考虑停。5–10是默认软目标，不是用户暗中提出的硬配额。小范围活动确实稀少、或明确偏好非常集中时，可在原合同允许的调整规则内交付更少项目，必须记录已检查范围与调整依据；不能把登录墙、重复搜索或工具失败当作“确实只有这些”的证据。未达软目标本身不自动等于任务失败，completed仍取决于用户要求和证据；明确的20项硬要求不可下调。连续两批新合格结果少于所查候选的 20%，且没有仍可能改变推荐的重要缺口，可提出“收益已低”；每批至少实际检查 5 个独立候选才能用这个比率。小样本、重复页面、错误/登录墙不能虚报“搜遍了”。明确 20 个的任务只找到 8 个时不能因收益低判完成，最多 partial。

批次评估放进主 Agent 下一次正常决策请求，不为每个工具结果额外调用一个判断模型；最终交付仍走独立的无工具核验。“全部活动”等开放集合不能证明穷尽时，必须标明已检查的来源和范围。模型可提出增减搜索范围及理由，但宿主只允许在合同范围和剩余预算内调整；不得修改用户硬条件、自增硬预算或用自己写的摘要充当证据。新用户指令产生合同新修订；已执行副作用保留防重，不重做。

#### B 的评分与 evaluation

先合格，再排序。推荐项评分为透明的相对排序值，不是概率或“完成了 87%”：

- 需求匹配 40 分：用途、地点、时间、预算等软偏好；明确硬条件另行 pass/fail。
- 证据充分与时效 30 分：原始来源、实际读到的字段、更新时间、冲突状态。对本人发布的公开活动按内容核验，不按平台名扣分。
- 可行动性 20 分：能否实际参加/购买、报名/库存/费用信息是否齐。
- 与其他推荐互补 10 分：前三避免全是同类型或同渠道转载。

建议主推门槛总分 75，且证据项至少 20/30；备选 60 且基本参加/购买条件已核实。阈值只作初始配置，离线校准后调整；不足时如实说没有足够合格推荐，不能偷偷放宽或造分。每个评分保留依据字段和证据 ID；模型的理由与分数不一致时降为待核对。集合评估另外检查“是否覆盖用户所有要求”，不能把若干项目平均高分当成任务完成。

### C：多路探索 + 独立评审

适用于用户选择深度研究，或合同涉及高价值采购、明显冲突、复杂多城市行程。默认 2–3 个只读成员分别搜官方/本地社区/专业来源，各自首批 5–8 个候选；合并去重后重点核实约 10–20 个。明确要求数量仍覆盖默认。不能让三名成员各自写一遍全部答案。

软检查点建议为总计 6 分钟或 40 次工具调用，三名成员的消耗合并计数，不各获一份完整总预算。独立评审只看合同、结构化候选和真实证据，先独立排序，再看协调器推荐；最多 2 次有针对性的补查，原预算内运行。评审不可派生副作用，也不能把“另一模型同意”当事实证明。输出仍按用户要求简洁。适合做 B 的可选增强，而非所有聊天必经的第二个大模型。

## 可验证的评估计划

“运行时 evaluation”和“产品上线前评测”分开。前者判断当前任务；后者检查这套判断是否可靠。先不追求一个总分。

- **确定性夹具 36 个**：活动 12（转载去重、home party、跨时区、过期、售罄、登录墙、仅摘要、冲突、少量真实可用等）；商品 12（20 条精确数量、变体、商家去重、运费/币种、缺货、规格未知等）；混合任务 8（日期→地点→天气→推荐、预算变化、取消、补充需求）；对抗 4（网页诱导放宽条件、虚构引用、成员自述、伪造成功）。断线/分页/重复写等 R1–R7 回归独立保留。
- **真实任务校准 12 个，每个 3 次**：先对三个方案做离线回放，再对选定候选安排 36 次真实运行；若确需三个方案完整在线对比才扩大为 108 次，不能每次小改都跑。固定问题、模型连接、资源预算与尽量同时间的采样窗口，记录来源快照与模型/连接/配置版本；不同实时网络结果不直接当方案退步。先以低成本离线回放淘汰明显差方案，真实调用需在现有授权与预算范围内安排，当前尚未执行。
- **硬门禁**：确定性夹具不允许假完成、无证据事实、越权、重复副作用、漏取消或旧端数据损坏；明确数量不足必须 partial。对这些用底层计数器，不用“模型说没执行”。
- **质量指标**：硬条件满足率、实体重复率、引用支持率、真实有效数、前三偏好命中率、重要缺口召回；运行指标记录端到端 p50/p95、总调用、输入/输出 token、费用和触顶比例。
- **评分校准**：先由人工独立标注可接受/不可接受及前三取舍，盲评方案顺序。评审模型只能辅助，不能自己出题自己判满分。初始真实样本很小，只报告样本数与区间，不把一次成功称为总体成功率。稳定后再设误判率阈值；硬性错误发现一例即回退该变更。
- **停止策略专项**：同候选集分别设置“推荐几个 / 找满20 / 尽量全面”，验证不同合同产生不同停止点；信息不足不允许高分强行过关；资源触顶仍交付已核实结果、缺口及继续入口。

## 架构落地与 UI

共享模块负责 `TaskContract / CandidateLedger / Evaluation / StopDecision / BudgetAllocation`，Node / Swift / Kotlin 只提供工具和请求、时钟、取消与持久化适配。所有数字来自同一份版本化契约，可在高级设置调整有意义的偏好；不按模型名 / 字数推断任务复杂度。

协调链路：理解原目标 → 合同 → 分派当前最重要缺口 → 收真实观察并实体化 → 合格过滤 / 排序 → 检查覆盖与收益 → 继续或交付。主 Agent 的人设只影响表达，不改变证据/权限判断。检查器无工具，禁止把交接文本当已执行凭证。

两端任务空间显示“发现 12 · 已核实 7 · 推荐 3”，并注明这些是实体数；工具调用、耗时与费用另列。可展开查看筛掉的原因、待核实字段和预算。比例只在分母有明确任务定义时显示，例如“已核实 14/20”；开放推荐不显示虚假的完成百分比。用户可以选“快速 / 标准 / 深入”，不需要看算法参数。桌面与手机执行及 UI 同步验收，旧端不认识的新合同仍保留原数据并给兼容状态。

## 选定后的实施顺序

1. 共享契约与账本：先定义任务合同、候选实体、字段证据和停止原因，接入确定性夹具；明确硬要求/软目标与合同修订，保留已有账号和历史回执。
2. 路由与资源分配：复用现有四岗位，按缺口分派和回收观察；父池统一计费，成员申请续额需要说明待补字段及预期收益。把散落数字移入共享策略配置，使 Agent 设置和实际生效范围一致。
3. 评估与交付：实现硬条件门槛、可解释排序、低收益停止和无工具收尾。首先只启用所选方案；C若作为深度模式，增加评审前需验证成本确有收益。
4. 双端行为与UI：桌面、iPhone、Android使用同一计数/停止契约，展示发现、已核实、推荐和缺口；不能只同步设置但手机仍执行简化逻辑。再跑来源故障/取消/恢复的端到端回放，以及选定的真实任务校准。

推荐选择 **B**，用 A 的模板初始化合同；C 留作 B 的深入模式。选择后再实施这套新策略，不提前把建议数字写进运行逻辑。
