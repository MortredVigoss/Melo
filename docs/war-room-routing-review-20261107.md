## 问题（按严重程度）

### P1-1 简单问题被套上 5–10 个实体的合同，又不许降低，直到预算用尽

- `shared/agent/taskEvaluation.js`：
  - `TASK_EVALUATION_POLICY.modes`：快速 3–5、标准 5–10、深入 8–15；
  - 合同建立时默认 `standard`（第 56 行：没有明确数量时取 `p.modes[mode]`）；
  - 冻结规则把评估器自己定的目标也当作「用户目标」，不许下调。
- 结果：一个只要说清「有什么」的问题，被要求凑满 5 个具名实体。凑不到就一直搜，直到预算耗尽，回答反而只有部分。
- 没有「足够回答就停」的判断，也没有对同一内容多个来源的合并：同一活动、同一品牌在多个网站出现时，各算一次「读取」，却凑不出新实体。

### P1-2 路由主 Agent 自己干活，成员额度太小，分派形同虚设

- `shared/agent/internalRouting.js`：
  - 路由说明写的是「简单或单步请求直接回答」；
  - 主 Agent 手里同时有原生网页搜索，于是大量检索由主 Agent 自己做（这次 11 次原生搜索）。
- 成员额度：
  - 默认 4 轮、8 次调用（`member.calls: 8`），第二次分派只给 2 轮；
  - 成员在第 60 s 就被打开网页的额度卡住，还没读完就中断。
- 这和「路由 Agent 只调度、子 Agent 去搜」的设计不一致。

### P1-3 小红书 / 抖音等社交检索在手机上根本不可用，路由也不会主动选它们

- `internalRouting.js` 的检索成员工具清单里有 `mcp:melo-xiaohongshu:*`、`mcp:melo-douyin:*`、`mcp:melo-public-media:*`。
- 但第 45 行要求工具「在本机可用」才会分给成员：
  - 手机直连没有 MCP，这些全部被过滤，成员只有网页搜索、打开网页、截图；
  - 桌面上还要求当前 Agent 的能力里勾选了对应 MCP 服务器（`capabilities.js` `toolCapabilityAllowed`）。
- 路由层没有「这类问题适合社交平台（体验、口碑、现场帖子）」的判断。选不选小红书，全靠检索成员里模型自己的倾向，不是路由层的决定。

### P1-4 成员自己用的整页截图被挂到回复里，用户看到一张几乎全白的图

- 检索成员第 57 s 对官网做了 `web_screenshot`（`fullPage=true`）。存下的图 932×4096，几乎全白。
- `ios/Melo/ChatStore.swift`（约第 1023 行）的设计是：一次回复中截的所有图都绑定到这条回复。
- 所以成员为了「看页面找链接」截的图，被当成回复附图展示给用户。图片登记在 `Images/index.json`，对应这条回复的消息 ID。
- 不是生成图片功能触发的。运行记录的 `requestedImages: 1` 只是 `ExecutionRecord.swift` 的默认值。

### P2-1 手机上成员的调用全部被算到主 Agent 头上（蜘蛛主次颠倒）

- 手机记录里成员调用的 ID 是 `web:job-1:…`、`tool:job-1:…`。
- `src/shared/executionBoard.js` `jobIndex` 与 `src/shared/warRoom.js` `JOB` 都只认以 `job-N:` 开头的 ID。
- 结果：
  - 成员的调用全归主 Agent，于是主 Agent 的蜘蛛跑来跑去；
  - 成员蜘蛛没有自己的调用，一直停在星核表面；
  - 分派卡上成员的调用次数也是 0。

### P2-2 主 Agent 也有一只会出去的蜘蛛，和「路由在中间不动」的设计相反

- `sceneActors` 给主 Agent 自己的调用单独配了一只蜘蛛（C6 的设计）。
- 用户的要求：路由主 Agent 固定在中间，只有派出去的成员在动。

### P2-3 蜘蛛在任务仍在进行时消失

- 蜘蛛只在有「运行中」的调用时出现：
  - 主 Agent 的蜘蛛：`out: !!active`；
  - 成员的蜘蛛：只在分派阶段运行期间出现。
- 这次的情况：
  - 原生搜索在记录里到达时已是完成状态；
  - 模型思考的十几到几十秒里没有运行中的调用；
  - 两个成员分别在 98 s 和 194 s 中断。
- 所以运行后半程大部分时间没有蜘蛛在外面。

### P2-4 手机工具调用记录没有时间

- 运行记录里 23 条工具调用都只有 `id / input / module / name / output / provider / query / resultSummary / status`，没有 `startedAt` / `finishedAt`。
- 结果：
  - 作战大屏日志里这些行全显示 00:00；
  - 按时间排序、用时追踪对它们失效；
  - 「首个调用 / 最后调用」也取不到。

### P2-5 区域附加内容沿用旧嵌入式面板的浮层样式，盖在画面上、样式不统一、点画面关不掉

- `desktop-ui/executionPanel.css` 中四个附加内容都是 `position:absolute` 浮层：
  - 第 39 行 `.execution-search-trail`；
  - 第 66 行 `.execution-candidates`；
  - 第 100 行 `.execution-outcomes`；
  - 第 138 行 `.execution-reasoning-records`。
- 它们由 `executionPanel.js` 的 `regionExtra` 放进作战大屏的详情区，但绝对定位让它们跳出底部详情区，盖在三维画面上（用户截图一、二）。
- 样式是旧面板的，与作战大屏卡片不一致。
- 只能点卡片本身或「返回作战台」关掉；点画面空白处不会关。
- 桌面同样受影响。

## 修复方案

可以直接修的部分（单一方案，用户已要求修）：

1. **成员归属**：调用 ID 中任意位置的 `job-N:` 都认作成员 N（`web:job-1:`、`tool:job-1:`）。投影层与作战大屏共用同一个函数，补手机真实 ID 的测试。
2. **主 Agent 不动**：
   - 主 Agent 不再有出去的蜘蛛。它自己的调用表现为该区域亮起，词条从区域升起；
   - 星核在运行中有「思考」脉动；
   - 只有成员蜘蛛离开星核。
3. **蜘蛛不消失**：
   - 成员蜘蛛从分派到交接一直在外面，在最近一次调用的区域上小幅移动；
   - 没有运行中的调用时也不收回；
   - 成员结束才回星核。
4. **手机调用记录补时间**：`ExecutionRecord` 记录手机工具调用的开始与结束时间，原生搜索事件记到达时间；旧记录没有时间的照常显示。
5. **区域附加内容**：
   - 在作战大屏里改为跟随详情区的普通排布，用作战大屏的卡片样式（统一）；
   - 点三维画面空白处、或点作战大屏任意非控件处，关闭区域详情；
   - 桌面与手机同一份。
6. **内部截图不进回复**：
   - 成员或主 Agent 为了读页面截的图，不挂到回复上；
   - 只有用户要截图，或最终回答明确引用时才展示；
   - 近乎纯色的截图直接丢弃；
   - 整页截图限制高度。

需要用户拍板的部分：

- **A. 没有明确数量时的停止规则**。推荐 A1：
  - A1（推荐）：
    - 没有明确数量的问题默认用快速档，3 个合格就可以交付，最多 5 个；
    - 用户原话里有数量的，照原话冻结；没说数量的目标可以由评估器下调；
    - 同一实体在多个来源出现只算一个，保留排名靠前的主流来源；
    - 连续两批没有新增就停。
    - 预计这类问题 1–2 分钟内返回。
  - A2：保持 5–10，只加一个硬时间点（例如 90 s）强制交付。实现简单，但结果数量和质量都不稳定。
- **B. 手机上怎么用小红书 / 抖音等桌面独有的 MCP**。推荐 B1：
  - B1（推荐）：
    - 手机能连上这台 Mac 时，需要这些工具的检索分派交给桌面执行（远程成员），结果回到手机；
    - 连不上时只用网页检索，并在回答里说明社交平台没查；
    - 同时在路由层新增「社交检索」岗位，路由判断这类问题（体验、口碑、现场、清单）时派它出去，不写死网页检索；
    - 桌面默认给 Agent 勾上这些 MCP。
  - B2：手机不接 MCP，只在桌面上生效。改动小，但手机上的问题依旧。
  - B1 涉及跨设备执行，规模较大，需要单独的方案与测试。
- **C. 主 Agent 是否还自己做检索**。推荐 C1：
  - C1（推荐）：主 Agent 不再持有网页搜索，只负责路由与评估，检索一律派成员；成员额度按任务放宽（例如 6 轮、16 次调用）。
  - C2：保留主 Agent 的简单直接检索（单一事实一步可答时），复杂检索才派成员。

### 直接修复

- **成员归属、主 Agent 不动、蜘蛛不消失、区域卡片**：第一步提交 `d98e7642`。
- **手机调用时间**：
  - `ExecutionOperation` 新增 `startedAt` / `finishedAt`；
  - 网页工具开始时就记为「进行中」，结束后原地更新；已结束的调用不再被改写；
  - 失败的调用保留打开时的网址；
  - 旧记录没有时间，照常解码。
- **成员原生搜索的归属**：
  - `AgentLoopHooks.onMemberJob` 告诉宿主当前是哪个成员在运行；
  - `ExecutionObservation.taggedForMember` 给成员的原生搜索加上 `job-N:` 前缀；
  - 每次模型请求的观测各自独立，所以主 Agent 之前的调用不会被改标。
- **截图**：
  - 只有用户要求看页面时，截图才附到回复下方（`WebPageText.userWantsScreenshot`）；
  - 近乎纯色的截图直接丢弃（`ScreenshotQuality.isNearlyBlank`）。判据是灰度图 1% 与 99% 亮度分位之差小于 16；当晚那张白图实测为 5，普通页面在 180 以上；
  - 工具说明加了一句：找内容或链接用 `open_url`，不要靠截图。

### A1：停止规则

改动在 `shared/agent/taskEvaluation.js`。

- **默认快速档**：
  - `TASK_EVALUATION_POLICY.defaultMode = 'quick'`：3 个合格即可交付，最多 5 个；
  - 三端的默认值都改为快速；Agent 设置里仍可选标准或深入。
- **桌面一次性迁移**：
  - 旧的加载流程会把当时的默认值 `standard` 写进每个 Agent，用户数据目录里的 6 个 Agent 全是 `standard`；
  - 新增一次性迁移（`settings.evaluationDefaultVersion = 1`），把这些由系统写入的值改为默认值；之后手动选择的深度一律保留；
  - 设置界面也能手动保存「标准」，所以来源无法完全证明（`git pp` 评审因此提出）。用户 2026-11-07 确认采用这次一次性迁移；
  - 手机上的 Agent 没有存这个值，不需要迁移；
  - Android 序列化时会写入默认值，已经存下的 `standard` 保持不变，因为无法区分是不是用户选的。
- **只冻结用户原话里的数量**：
  - 没有明确数量的合同可以在同一轮里修正，但只能增加要求：可以加条件、必填字段、覆盖标签，或补上漏掉的用户数量；
  - 类别不能改，已记录的条件、必填字段和覆盖标签一个都不能删；
  - 有明确数量的合同照旧冻结。
- **软目标可以下调**：
  - 有引用证据的调整会立即下调软目标；
  - 连续两批「读了新页面，却没有新增合格实体」时停止搜索，交付已核实的部分并说明缺口。只读到重复实体也算这种情况；
  - 页面按「规范化网址 + 正文」识别：同一页面换个调用或成员重读，只算一次读取；翻页或正文有变化，算新的读取；
  - 搜索停止后，至少要有一个达到备选分数的合格实体才算可以交付。只是合格、但模型判为不相关的实体不能当作答案。
- **同一实体只保留一条**：保留第一个核实的来源（通常是排名最靠前、最先读到的结果），后来的网站只补缺失字段。
- **复核规则同步**：没有明确数量时，账本给出 `ready_for_review` 后，复核不再要求更多候选。

### C1：主 Agent 只路由

- **收走检索工具**：
  - 只要存在检索成员（检索或社交检索），三端都把这些成员的全部工具和原生搜索从主 Agent 的请求里拿掉；
  - 主 Agent 直接调用这些工具会被拒绝，并提示改用 `route_task`。
- **路由说明**：
  - 主 Agent 负责路由、分配、评估与汇总，检索一律派给成员；
  - 成员额度改为 6 轮、16 次调用，数值取自策略，不再写死。
- **路由关闭时归还**：用户补充消息会关闭本轮路由，此时检索工具还给主 Agent。桌面由 `restoreLeadRetrieval` 处理；手机与 Android 按当轮路由状态计算。
- **桌面成员的检索方式**：
  - 默认仍用 Melo 自己的网页检索与读取，沿用 `dbf5dff4` 的取舍（证据可读、token 少得多）；
  - 桌面默认检索后端是浏览器检索（`browserFallback: true`），所以收走主 Agent 的原生搜索后仍能检索；
  - 只有在 Melo 自己的搜索不可用（关掉浏览器检索、也没配 HTTP 后端）且原生搜索已验证时，检索成员和社交检索成员才接管原生搜索，主 Agent 仍只负责路由。这是第二次 `git pp` 评审后用户的选择。
