## 2. 已确认的问题

### P1：桌面整组选得很多，却漏掉已知的跨目录安全测试

`desktop-ui/app.js` 或聊天 controller 的改动只选择桌面与 iOS JS。`src/safety/fileSafetyGate.production.test.js` 明确读取这两个文件，检查文件安全审批的请求类型、SSE 分流与界面接线，但不会被选中。该关系已登记在架构注释中，`scope` 也会报告它；日常选组仍忽略它。

证据：[选组](../scripts/test-plan.js) 18–23 行、[安全测试](../src/safety/fileSafetyGate.production.test.js) 24–27、63–84 行、[依赖注释](../architecture/module-annotations.json) 的 `source-tests-app-js` / `source-tests-chat-feature`。本轮断言确认该测试被发现但不被选中；未声称当前产品安全功能已损坏。

### P2：后端没有按功能缩小的分支

`test-plan.js` 20–21 行只豁免 `desktop-ui/`、`ios/Melo/`、`ios/Tests/`，后端、同步、脚本等普通改动一律进入全量。即使只改一个搜索结果辅助函数，也同时跑语音、图片、记忆、设置浏览器和 Swift。

对权限、状态持久化、模型执行、共享协议等核心改动扩大范围有必要；普通功能叶子与核心改动采用相同策略，是效率问题。[scope](../scripts/scope.js) 开头明确“只报告，不改变选组”，不能因已有功能地图就认为已实现增量回归。

### P2：开发元数据与说明文档被当成产品代码

架构地图和手工注释 JSON 触发全套产品回归。功能目录 README 不在文档白名单，触发全部桌面测试及浏览器。`5872d7d` 是现成例子。

地图需要生成一致性、所有权与隐式依赖登记检查，不能简单跳过；建议独立 tooling 档，运行生成器 / scope / selector 检查。只对已核实不被运行时读取的 README 扩充文档规则，不能一刀切豁免所有 Markdown 或 JSON。

### P2：共享工作树与较旧基准扩大任务范围

`test-plan.js` 41–48 行收集全部暂存、未暂存和未跟踪文件，不区分线程。一个线程改 CSS，另一个线程留下后端 WIP，就变成全量。显式旧 `--base` 同样把基准后的所有变化纳入；这是命令的实际语义，不能直接将其他线程文件排除后仍宣称整个工作树验收通过。

建议提供明确的“本任务定向检查”和“共享树集成检查”，分别报告基准与覆盖范围。干净树重复检查最后一次提交是防止空跑的现有保护，但没有已验证内容回执，因此同一状态也会反复重跑。

### P2：iOS 原生与资源没有分开

日常 runner 只传 `--renderer-only` 或不传选项。虽然 [iOS runner](../ios/scripts/test.py) 已支持 `--suite`，日常检查没有使用它；任何 `ios/Melo/Scene/scene.css` 变更也触发全部 Swift。

桌面独有 `surfaceUnify.css` 不在手机资源 manifest 中，却仍触发 iOS 渲染校验。应按共享资源输入、原生源文件及共享协议分别选择。Swift 编译缓存已存在且每次仍执行测试；不能把“有缓存”等同于无需选择范围。

### P2：便宜的预检太晚，失败后从全量开头重跑

[日常 runner](../scripts/verify-daily.js) 30–37 行先 JS 全量，再语法、文档、浏览器，最后才检查手机资源 manifest；地图一致性也混在全部 JS 中。

## 3. 建议落地顺序

下列是审计建议，尚未实现，不改变现行 gate。

1. **先修已知遗漏并提前预检。** 桌面修改补入已登记的跨目录源码读取测试；在昂贵阶段前检查改动语法、地图一致性、共享契约生成与资源 manifest。先把“为什么选中 / 为什么全量”的路径和规则打印清楚。
2. **拆开成本很明确的检查。** 开发元数据走 tooling；手机纯资源走渲染；Swift 按实际输入选 suite；设置浏览器只由设置或其共同依赖触发。消除重复 iOS JS。对未知路径仍回退扩大范围。
3. **再实现真正的功能影响选组。** 选择受影响功能测试，并沿已验证的反向依赖、路由注册、源码读取、生成器、原生桥和共享协议补齐调用方。不能直接拿 `scope.focused` 当完整清单，也不能只用文件名或直接 import 猜测。地图失效、删除 / 重命名、无法解析的依赖应扩大检查。
4. **最后处理重复运行。** 增加任务文件范围与共享树集成范围；只有源码、测试、依赖、工具链及全部相关输入指纹一致时，才允许明确显示“复用已有成功回执”。更稳妥的第一步是使用现有编译缓存和精确选组，暂不缓存复杂运行结果。失败、未完成或未知依赖不能复用为成功。

建议的日常策略：

| 改动风险 | 日常检查 |
| --- | --- |
| 纯说明文档 | 相对链接检查 |
| 开发元数据 | 地图 / 选组 / 生成器相关测试 |
| 局部 CSS / 页面 | 相关界面与关键交互；影响共享资源时加手机渲染 |
| 单一后端功能 | 该功能单元 / 集成 + 反向依赖 + 相关接口契约 |
| Swift 局部 | 受影响 suite；涉及共享契约时补另一端 |
| 权限、状态持久化、执行循环、公共协议、依赖 / 构建或未知边界 | 扩大到对应跨功能 / 全量 JS 与必要平台检查 |
| 发布 | 保持完整发布 gate，含打包、安装、启动 |

验收新选择器时应覆盖：纯文档、元数据、局部 UI、已知安全跨目录边、后端叶子、共享契约、iOS 资源 / Swift 区分、删除 / 重命名、新文件、未登记隐式边、共享 WIP、旧基准、失败回执不复用。用一组代表性变更对照全量作校准，不能用“选得少且绿色”单独证明正确。不要为了降数量删测试、随意跳过失败用例或降低原断言。
