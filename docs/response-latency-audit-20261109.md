# Melo 提问到回复的延迟审计

日期：2026-11-09（Australia/Melbourne）。用户确认电脑和 iPhone 都慢。本次审计产品源码基准 `84437476`，开工共享树干净。只增加审计文档和本地脱敏证据，不修改运行逻辑、配置、账号、聊天或已安装应用，不请求新模型、不推送。

## 结论与证据边界

主要成本是多次串行模型请求、先写缺乏证据的答案再纠偏，以及 iPhone 正文延迟展示和串行读取。单纯增加/减少最大轮数不能解决正常任务的延迟。需要保留用户已经决定的“主 Agent 路由、审核、整合，检索交给成员”，以及用户自己选择的模型。

当前源码已关闭智能选模，没有每轮自动轻模型分类再选回答模型的额外请求。桌面 `prepareNode` 的旧注释仍提到分类 API，不代表当前实际调用。准备阶段的记忆向量最多等 2.5 秒，压缩可能调用模型，但不能据此归因为每轮都多等这些时间。

本次真实耗时来自已有本地记录：桌面 11-05、iPhone 11-07（应用 0.7.16/0.7.17）。0.7.18 的覆盖安装备份保存了这些历史记录，不代表它们是在 0.7.18 上新跑的。对应瓶颈仍在当前源码中。没有把旧数据报告成今天的测速，没有把确定性测试当真实模型验收。

## 实际时间分解

### iPhone：单一天气查询

11-07 的天气查询，总计 **85.506 秒**，**9 次模型请求、3 次网页调用**。

| 环节 | 观测耗时 | 说明 |
| --- | ---: | --- |
| 主 Agent 分派 | 4.75 秒 | 首次模型请求，输入 12,249 token |
| 检索成员 | 49.17 秒 | 3 次模型请求约 25.08 秒；3 次读页 23.877 秒，其中一次 20.044 秒超时 |
| 主 Agent 整理候选答案 | 7.00 秒 | 此时已有可回答的天气数据 |
| 第一次完成检查 | 8.72 秒 | 正确发现候选答案加入了证据不支持的时段、更新时间等信息 |
| 改写 | 6.97 秒 | 没有新工具调用，删除未证实内容 |
| 第二次完成检查 | 5.87 秒 | 通过 |
| 不确定内容再核验 | 2.37 秒 | `finalize-verification`，在完成检查之后再次请求模型 |

全部模型请求合计 **60.754 秒**，网页调用 **23.877 秒**，余下不到 1 秒为本机准备/记录/转换等间隙。候选答案之后的检查、改写和再检查约 **23.93 秒**。核验确实拦住了无依据内容，不能直接删除核验以降低耗时。

### iPhone：活动攻略与中断恢复

同日活动攻略记录显示 **766.044 秒**，实际有三段运行。三段 Trace 共 **337.168 秒**，段间等待 **428.876 秒**；运行事件显示两次进入后台、请求结束、回前台后继续。只有 5 次实际读页，合计 **12.166 秒**；17 次模型请求尝试中 15 次返回、2 次取消。

第一段在第一次检查指出“缺少票价、地点、场次等来源”后，下一次模型又用 **36.43 秒**生成答案，没有新增读取，再用 **7.93 秒**检查后仍因同样的证据缺口退回。这里是可避免的无效改写循环。另一段成员限额交付单次用了 **41.11 秒**。总时间不能全部称作“思考时间”，也不能承诺 iOS 后台无限运行。

### 桌面已有样本

11-05 一个完成的检索回合耗时 **35.681 秒**，5 次模型请求合计 **31.924 秒**，占约 89%。这是旧记录，只用于证明桌面确有模型往返占主导的样本，不能作为当前版本的平均延迟。

## 当前源码确认的问题

### P1：iPhone 网络在流式返回，聊天正文仍等整轮完成

- `ios/Melo/ChatGPTAccount.swift:readStream` 只回传 observation、receiving 和状态，没有正文 delta 回调。
- `ios/Melo/ChatStore.swift:send` 的执行分支等 `account.reply` / `Network.reply` 返回后才创建 assistant `ChatMessage`。
- `ios/Melo/Network.swift:reply` 的 Chat Completions / Anthropic 请求仍写 `stream:false`。
- 桌面 `/api/chat/send/stream` 已有 `onDelta`。因此两端的首字体验并不一致。手机不能用“已连接 SSE”宣称正文已流式显示。

### P1：完成检查范围宽，且检查之后可能再次请求模型

- `shared/agent/goal.js:goalCandidate`：只要有可用工具且不是纯问候/明确自包含请求，就会进入检查；确定性探针中“解释二分查找”零工具调用也进入 `checking`。
- 桌面 `src/services/chat/execution/invokeModelNode.js` 主循环执行 goal check，`src/agents/subAgent.js` 成员交接前也执行自己的 goal check。
- 手机 `ios/Melo/AgentLoop.swift` 成员无调用时直接交接，没有照搬桌面普通成员检查；主 Agent 仍检查，达到上限时另有收尾请求。
- 两端 finalize 仍可根据不确定标记再做一次 `verifyUncertainClaim` / `PhoneUncertainty.verify`。这不是每轮必发生，但天气样本实际发生。
- 当前修复反馈主要通过 prompt 传回模型；缺少证据时，模型仍可再写一份没有新增证据的候选，重复支付生成与检查成本。

### P1：iPhone 同批独立读取和内部岗位没有并行调度

- `ios/Melo/AgentLoop.swift` 的 `route_task` 分支要求 `calls.count == 1`，进入单个 `job`，完成后才恢复主 Agent。
- 同文件工具执行是 `for wire in calls` 内逐次 await。天气样本一个 20 秒读页超时挡住了同批另一个 1.38 秒读取。
- 桌面 `internalMembers.js:runInternalMembers` 已有只读 lanes；`src/tools/executor.js:executeToolCalls` 对声明并发安全的工具分组并行。模型若分轮派发，桌面仍会串行。
- 不能直接对所有工具使用 Promise.all/TaskGroup：写入、审批、依赖步骤、共享 WebView 必须保留顺序和隔离。

### P2：普通任务带着较大的主 Agent 上下文多次往返

- 天气首轮 12,249 输入 token；主 Agent 后续请求的序列化 JSON 约 40–41k 字符，成员约 2–22k 字符。
- 攻略主 Agent 请求约 36–59k 字符。字符不是 token，未按字符粗算账单。
- 准备节点包含人设、历史、资料、记忆、执行历史、工具协议等；成员背景已在 `subAgent.js` 收缩，不能笼统声称每个成员都带全量主提示。
- 优化重点是按职责形成稳定前缀、紧凑事实交接和只传当前缺口。禁止清空用户记忆或粗暴截断证据以达成输入指标。

### P1（可观测性）：手机执行面板没有展示全部模型耗时

- `ExecutionObservation` / transport 复用 `model:response`；`ExecutionRecord.mergeStage` 对已终结的相同 id 直接 return。
- `taggedForMember` 只给 operations 加 job 前缀，没有给模型 pipeline 加每次请求/成员唯一标识。
- 天气 Trace 有 9 次模型请求，但执行记录只有一张 `model:response`，耗时 4.685 秒；攻略只有 5.649 秒那张。后面的请求没有按独立请求呈现。
- `LoopTrace.model` 将 `firstEventMs` 固定记 null，所以无法从该 Trace 得到每轮首字延迟。原 pipeline 的 firstEvent 也不是用户看到正文的时间。
- 总耗时包括后台暂停，应分别展示总用时、活跃执行、等待恢复、模型/工具耗时（并行不能简单相加冒充墙钟时间）。

## 优化顺序与验收方案（未实施）

1. **先补全每轮计时和正文通路。** 三端共用 run/member/request ID，区分发出请求、首网络事件、首正文、候选完成、核验完成、界面呈现。iPhone 补 API SSE、正文增量与暂存交付；内部成员只展示事实进度，不把交接报告混进用户答案。候选经过核验才成为正式交付，取消/改写/重启不遗留伪完成消息。
2. **减少无效生成，保留主 Agent 审核。** 分派携带需要的字段和证据要求，成员返回紧凑的已核实字段/来源/缺口。将修复分成“只需改措辞”和“必须补证据”；后者先执行针对性检索，缺口无变化不能反复输出长答案。整合 goal check 与不确定内容核验，避免已覆盖的断言重复审。简单自包含答案走明确可审计的短路径，模糊/外部操作继续核验，不能靠几个关键词绕过检查。
3. **两端并行与取页策略对齐。** 独立只读任务先允许 2 个并发；每个请求有独立取消/超时和回执，依赖与副作用顺序不变。网页正文就绪即可结束或在软超时使用另一可信来源，硬截止保留。HTTP 直接读取可用时先直接取正文，再按需用 WebView；不能把没读到的内容当作证据。
4. **再优化提示与缓存。** 测量稳定前缀/输入分布和实际 cache hit，按岗位收窄重复指令；正文复用必须绑定 URL、内容版本、时效、权限和原始证据。已有事实可复用，完成回执不能作为事实来源。当前选择的模型和连接始终保持，自动选模不恢复。
5. **后台恢复单独优化。** 展示“已暂停，回前台继续”；保留已完成读页和工具回执，恢复后只补未完成步骤。不能将用户离开应用的数分钟归咎于模型，也不能通过重启重复已成功副作用。

建议验收目标是同一模型/连接下的候选指标，必须实测后确认：

| 场景/指标 | 建议目标 |
| --- | --- |
| 普通自包含问答 | 正常 1 次生成；确需证据或存在歧义时再检查 |
| 单事实检索 | 正常 5–6 次以内模型请求（分派、成员、整合、统一核验），异常补查单列；天气样本基线 9 次 |
| 正文显示 | 收到可展示正文 delta 后 200 ms 内更新；内部工具参数/成员报告不显示为答案 |
| 并发只读测试 | 两项互不依赖读取的耗时接近较慢项，而非两项之和；慢项不阻塞已完成项回执 |
| 真实回合延迟 | 对照集总耗时中位数争取降低 30%；同时记录 p95、首正文、模型请求数、token、暂停时长 |
| 质量与权限 | 原始要求、证据支持率、来源可打开率、明确数量、取消及副作用防重不得退步 |

对照集至少含普通聊天/解释、天气等单事实、活动/商品多项、失败来源、后台恢复。公开合成任务在固定模型下重复，区别冷/热缓存与前后台；保留完整证据与失败结果。当前没有运行新模型性能基准，不承诺固定秒数。

## 执行链、覆盖与停止边界

- 桌面：聊天发送 UI → `src/http/chatRoutes.js` → `sendChatMessage`（state/会话队列）→ `chatExecutionRunner`（预算、权限快照、Trace）→ `prepareNode`（记忆/历史/上下文）→ `invokeModelNode`（路由/模型/工具/goal check）→ `internalMembers` / `subAgent` / `executor` → `finalizeNode` → 原子保存消息 + SSE。
- iPhone：`ChatStore`（历史/连接/执行记录/checkpoint）→ `ChatGPTAccount` 或 `Network` → `AgentLoop`（单岗位切换/工具/检查/收尾）→ 模型 transport / `WebPageTools` → finalize → `ChatStore` 保存消息；`ExecutionRecord` 和 `LoopTrace` 各自投影观察。
- 共享契约：`goal.js`、`internalRouting.js`、`taskEvaluation.js`、`shared/protocol/agent-loop.json`。核对目标/预算/取消/证据边界，未改变线协议。
- 覆盖：上述函数的等待/循环/显示路径、真实数据的脱敏耗时复算、当前固定选模入口、已有 28 项目标/路由测试。
- 未覆盖：新真机/真实模型跑分、Android 原生执行路径、远程频道、图片/语音生成专用路径、供应商内部排队/推理、WebKit 内部网络。原因是用户本轮要求审计现有两端聊天延迟；现有记录不能分解供应商内部耗时或代替新版本跑分。
- 停止条件：到模型/网页传输边界、消息落盘和已读记录为止。当前 source → host 调用关系可核实，第三方内部机制不猜测。不把后台恢复间隙当作 CPU 或网络忙碌时间。
