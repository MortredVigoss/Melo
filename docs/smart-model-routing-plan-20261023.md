# 智能模式：按复杂度 / 风险分流模型，并下线「额外快速」· 2026-10-23

来源：2026-10-23 主线审计（Claude）。用户结论：「额外快速」是把推理层的"小模型先猜、再掷骰子"（speculative decoding）思路错放到了 harness 层，要整体去掉；换成一个判断问题复杂度和风险、再把这轮交给合适模型的"智能模式"，**模型档位不得写死任何模型名**。

## 1. 审计：「额外快速」现在是什么

**判定**：它既不是 speculative decoding（那要在 token 级由推理引擎做），也不是模型分流——它只是用一个按名字猜出来的"小模型"做两个粗标签，换来每轮最多 4 秒串行等待和额度消耗，而答案模型始终不变。整体下线，功能由下面的智能模式承接。

## 2. 目标与原则

1. 每一轮先判"这个问题多难、风险多大、需要什么能力"，再决定交给哪一档模型；判断结果可见、可解释、可被用户覆盖。
2. **档位来自用户的实际配置**（已保存连接 × 其模型目录），代码里不出现任何模型名；现有 `hint()` 的名字正则随「额外快速」一起删除。
3. 长度不等于难度：短句但任务复杂（换图片背景、改代码、多步工具、深度检索）按任务形态判，不按字数。
4. 风险优先：高风险（医疗 / 法律 / 财务 / 不可逆操作 / 手机操作 / 发送消息 / 删改文件）一开始就上强档，绝不中途降档。
5. 失败安全：判断不可用时退回"当前默认模型"，行为与今天一致；判断只允许发给用户允许的连接，默认只用对话本身的连接（不把用户消息发给别的平台）。
6. 用户明确指定的模型永远优先：Agent 钉死的模型、对话里手选的模型都不被分流。

## 3. 设计

### 3.1 模型池与档位（不写死）
- 模型池 = `config.llmProfiles` 各连接 × `connectionModelOptions`（`desktop-ui/modelPresentation.js:14`）同源的目录（含 Codex `~/.codex/models_cache.json` 发现结果、API 提供方 `/models`、用户手填）。
- 三档：`light` / `standard` / `strong`。档位表存配置 `smartRouting.tiers = { light: [{profileId, model}], standard: [...], strong: [...] }`，每档可多模型，按顺序优先。
- 自动建议（只建议、用户确认后生效）：有 `modelPricing` 的按输出单价排序；没有的按最近实测延迟（取 `modelResponses` 回执里的真实耗时，不再做合成探测）；两者都没有 → 不建议，设置页提示"把模型拖到档位里"。
- 只配置了一个模型 → 三档同一个，设置页明示"智能模式当前等于固定模型"。
- 能力标注：视觉 / 图片生成 / 长上下文 / 工具调用来自提供方目录元数据 + 用户在档位表里勾选；`VISION_PATTERNS` 这类名字正则只保留为"目录无元数据时的回退"，并在 UI 可改。

### 3.2 分流判断（triage）
输出一个结构：`{ complexity: 1-5, risk: low|medium|high, needs: { vision, image_generation, image_edit, tools, web, long_context, code }, domain: factual|creative|coding|casual|task, reason }`。

产生方式（按顺序，前面能定就不往下走）：
1. **硬规则只定下限，不定上限**：
   - 风险下限：`agent-loop.json intent.patterns.highStakes` 命中 → `risk: high`；计划里有副作用工具（file_write / file_delete / file_move / bash / 发送类 / phone_use）或请求命中手机 / 导航 → `risk ≥ medium`。
   - 能力下限：带图片附件或 `inferImageTask` 判为编辑 / 生成（含"换背景"这类短句）→ `needs.image_*`，最低 `standard`；带文档附件 → 最低 `standard`；搜索计划为 deep research → 最低 `strong`。
   - 平凡下限：问候 / 简短确认 / 纯算术（沿用 `requestPolicy.js:82-95` 已有规则）→ `complexity: 1`，`light`。
2. **轻档模型做结构化判断**（只在规则没定出档位时）：用 `light` 档第一候选发一次 ≤3 秒、`maxTokens ≤ 200` 的 JSON 请求，输入 = 最新用户消息 + 最近 2 轮摘要 + 附件类型 + 可用工具类别；失败 / 超时 / 解析失败 → `standard`。同消息哈希 5 分钟缓存。
3. 档位映射（可在设置页调）：`complexity ≤ 2 && risk low → light`；`3 → standard`；`≥ 4 || risk high || needs.code || needs.image_edit → strong`。

### 3.3 升档 / 降档
- 升档信号：轻 / 标准档模型在回答开头输出 `[ESCALATE: 原因]`（提示词规则，与 `[UNCERTAIN:]` 同一套机制）→ 丢弃该次输出，用上一档重跑本轮，一次为限；工具循环超过 K 轮（默认 4）或触发 `REPEATED_TOOL_FAILURE` → 下一轮起升档；核验结果 `CORRECTED` → 本对话后续至少 `standard`。
- 流式：轻 / 标准档的第一段输出先缓冲 ≤400 ms 或 ≤120 字再放流，期间出现升档标记就静默切换；强档不缓冲。
- 降档：同一对话连续两轮 `domain: casual` 且无工具无风险 → 允许回到 `light`；用户手选或 Agent 钉死的不降。

### 3.4 用户控制
- 模型选择器（默认模型 / Agent 模型 / 对话模型）增加一项"智能（自动）"；选了它才分流，否则固定模型。
- 设置页"智能模式"：档位表（拖放模型）、偏好滑块（省额度 / 平衡 / 质量，调 3.2 第 3 条的阈值）、开关"允许中途升档"、"高风险直接强档"（默认开）、"判断只用对话连接"（默认开）、最近 20 次分流记录（复杂度 / 风险 / 档位 / 模型 / 依据）。
- 所有文案走 `ui`/`t()`，中英日韩西五语。

### 3.5 可观测与回执
- `execution_event`：`route:model`（替代现在的 `judge:intent`），output 形如"复杂度 3 · 风险低 · 需要工具 → 标准档 <model>（依据：轻档判断 / 规则 / 缓存）"。
- 回复回执新增 `routing: { tier, model, complexity, risk, basis, escalatedFrom? }`；`modelResponses` 已记录 requested / reported model 与用量，UI 回执里顺带显示本轮成本。

### 3.6 与现有分类的关系
- `intentRouter.js` 的五分类并入 triage 的 `domain` + `risk`：`intentRequiresVerification` ← `risk ≥ medium || domain === factual`；即时语音 ← `domain casual`；工具上下文 highRisk ← `risk high`；跳过记忆 ← 问候规则。`gpt-4o-mini` 这类写死的分类模型随之删除。
- `agent-loop.json intent.*` 保留给手机（`ios/Melo/AgentLoop.swift` 的 `PhoneIntent`）；桌面只用其 highStakes 正则做风险下限。手机采用分流是第二阶段。

## 7. 风险与边界

- 判断请求本身的隐私：只用对话连接或用户勾选的连接；不再像「额外快速」那样"可能发送给已配置的任何平台"。
- Codex OAuth 单账号：档位只是不同 slug，省的是时间不是钱；本地 Ollama 单模型：智能模式退化为固定模型，UI 要说清。
- 流式缓冲的 400 ms 会让轻 / 标准档首字稍慢；强档不受影响。
- 分流错判的代价由升档兜底；降档只在明确平凡的闲聊上发生。
- `VISION_PATTERNS` 等名字正则是既有债务，本方案只把它们降为回退并可在 UI 覆盖，不在 P0 清除。


## 8. 2026-10-24 代码复核与 UI 补充（Codex）

本节记录当前 `458c3c0` 的源码核对与用户新增要求；原 Claude 方案保留。本节与上文冲突的内容应在实施前采用下述约束收敛。当前仅完善设计，未下线旧功能、未改运行逻辑。

### 8.1 用户明确要求的选择器

- 同一个模型选择器并列列出「智能（自动）」和实际连接可用的固定模型，例如 **Sol 6.1 / Astra 6**；保留「沿用 Agent / 系统默认」。示例名称不是路由规则，模型选项仍从已保存连接与目录读取。
- 手选固定模型后不执行智能判断、不自动换模型；选择智能后显示「智能 · 当前连接」，每条回复显示实际回答模型，不能把智能当作真实模型 ID 发给提供方。
- 默认模型、Agent 设置、聊天输入区的入口与状态一致；修改只作用于后续请求。正在执行的一轮保留启动时的模式、连接、权限与预算快照。
- 保留现有「对话明确手选固定模型 > Agent 固定模型 > 系统默认」行为；智能路由不能覆盖已经生效的固定选择。Agent 固定模型使智能不可用时，选择器明确标注原因，不能选中「智能」后暗中固定。
- 智能设置提供三档模型分配和候选顺序；拖放同时提供可点击的选择/移动控件，手机和键盘用户无需拖拽。只配一个有效模型时显示「当前等同固定模型」并跳过额外判断请求。
- 回复记录区分判断调用、实际回答、升档前后和失败用量；显示「智能 → 实际模型」，发生升档时显示原因。普通固定模式继续显示其固定模型，历史回执保持可读。
- 桌面、iPhone、Android 同一模式与选择语义；手机必须有真实可用的选择器、设置和回执，不能只同步字段。连接未在本机配置时提示用户连接或改选，不静默使用别的平台。

### 8.2 原审计需要校正的事实

1. `fastJudge.js` 的模型名正则只是无有效实测结果时的排序偏好；已有有效实测优先，多个成功候选按延迟排序（`rankJudgeCandidates`）。不宜表述为始终按名字挑选。
2. `classifyIntent` 先命中规则则立即返回；只有灰区且开关开启时进入这套 4 秒判断，所以并非每轮都有这段等待。
3. 关闭或删除 `extraFast` 分支后，`intentRouter.js:141–166` 还有一条独立模型分类请求。P0 必须同时取消这条旧请求，否则删除界面后仍会产生隐藏的判断调用。当前这段用配置/环境指定模型，没有方案第 3.6 节所说的固定 `gpt-4o-mini` 分类模型。
4. 准确结论仍成立：旧判断只产出标签，不选择实际回答模型；它不是智能模型路由。

### 8.3 实施必须收敛的运行约束

- **升档接续，不能整轮重放。** 沿用原 run/turn、工具结果、成功副作用账本、权限确认及预算；工具结果全部配对之后才切换模型。现有 `shared/agent/turn.js` 仅在 `repairing` 下阻止同参数成功副作用重放，新升档必须接入该机制。不得重建空状态绕过重复失败/无进展/取消上限；“超过 4 轮”只是一次性候选信号，不能无限升档续命。
- **流式控制不能靠 400 ms 猜完整标记。** 标记可能拆分到多个 chunk，也可能在普通解释或引用中出现。优先采用专门结构化控制结果；若保留文本协议，必须严格限定助手控制前缀并跨 chunk 解析。已经展示给用户的内容不能静默撤回；工具输出和用户引用不得直接触发升档。
- **预算包含所有请求。** 轻档判断、实际回答、原有目标完成检查、升档和纠偏共享总时间/token/次数上限与停止信号。判断超时须真的取消传输；失败请求的已知用量仍记账。选择固定模式、单有效模型或规则已确定时，额外判断请求计数必须为零。
- **隐私约束涵盖回答和升档。** 仅限制判断请求不够；默认将判断、答案、升档候选全部限制在本轮绑定连接。跨连接必须由用户明确配置允许，不能因候选失败而自动改用另一端点；本地模型不可悄悄退到云端。缓存绑定 home、连接身份/版本、模型、规则版本、上下文和附件描述，不能只哈希最新一句。
- **能力优先于档位。** 档位不是工具授权，也不是视觉/图片编辑能力证明。先匹配真实任务能力与当前权限，再在满足条件的候选中选档。新模型上下文容量与协议须重新适配，保留原历史；失败时保留草稿/附件。不存在可用候选时明确说明，不用低档悄悄冒充强档。
- **统一回退。** 方案第 2 节写默认模型，第 3 节写标准档，应统一为：当前连接内满足风险/能力下限的标准档优先；不满足时向上选；只有当前固定默认模型满足要求才可作为回退。不能为完成回退降低已确定的风险下限。
- **风险和能力不看一句话。** 把本轮原目标、补充要求、附件任务和已有执行结果一起判定；“好的”不能把前一轮高风险任务降成闲聊。规则只设下限，再合并结构化判断，不能命中某条下限后丢掉其他风险/能力需求。实际工具调用仍独立执行权限与审批。
- **价格/速度建议不代表质量。** 输出单价与响应耗时只标为费用/速度依据；无法证明推理强弱，也不直接决定高风险档位。不同任务的耗时需注明样本数与统计范围；没有足够证据时由用户分档。
- **两端从 P1 共用决策核心。** P1 就把模式/档位/候选过滤/回退/升档预算规则放入 `shared/agent/` 并建立 conformance；P3 接入各端本机连接和 UI。模型模式是配置字段，不用虚构 `model = smart` 污染现有请求与同步；密钥与本机连接授权保持本地。
- **下线保留数据与必要覆盖。** 旧 extraFast 配置停止消费，读取不能重写其他账号配置；历史判断回执仍可读。删除专属页面/接口测试时，将取消、隔离、传输上限、失败草稿/修订冲突等仍适用的断言迁入新模块。额外浏览器验收线可并入设置旅程，但不是用删除覆盖来减少测试数量。

### 8.4 必须有的验收

1. 固定 Sol 6.1 / 固定 Astra 6 / 智能三种选择跨保存、重载、下轮发送保持一致；真实请求模型与 UI 回执一致。用虚构模型 ID 再跑同一用例，证明无名称依赖。
2. 固定模式、仅一个有效候选、规则足够明确：判断 HTTP 请求计数为零。
3. 短句“换背景”、带附件、“继续/好的”继承复杂或高风险目标，不被降到不适配的轻档。
4. 判断超时/坏 JSON/无标准档/候选下线，按唯一回退规则；终止后延迟回包不能发起答案或工具请求。
5. 当前连接限制覆盖判断、答案与升档：其他连接的服务计数为零；并发 home、同句不同上下文不串缓存。
6. 成功写文件或发送消息后升档，实际副作用计数仍为一次；权限拒绝或用户取消不能借升档重试。
7. 升档标记逐字符分片、迟到、用户引用、工具输出均正确处理；已经展示的正文不撤回。
8. 升档、目标检查与纠偏共用预算，总请求和费用记录完整；达到重复失败/无进展/时间上限就停止。
9. 桌面浏览器、Swift 与 Android 执行同一决策夹具；移动端具有固定/智能切换、分档配置与实际模型回执。
10. 旧账号/连接、聊天选模、Agent 固定模型、原图、历史回执保留；旧 extraFast 页面/接口不可达且无隐藏分类请求。
