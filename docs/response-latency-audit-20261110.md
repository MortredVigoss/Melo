# 回复延迟复核与当前版本实测（2026-11-10，Claude，只报告）

用户反馈：问一个简单问题（例如"明天墨尔本天气多少"）要等一分多钟到两分钟。Codex 在 11-09 做过一轮[延迟审计](response-latency-audit-20261109.md)，用的是 11-05 / 11-07 的旧记录，没有在当前版本上实测。本轮在当前代码（产品树 `897db8ab`，文档头 `a3d6859b`）的桌面版上用真实连接实测了三次，并逐次拆解每个模型请求。只审计与记录：没有改产品代码、配置、账号，没有推送或安装。

## 结论

当前版本在电脑上回答"明天墨尔本天气多少"实测 **105.5 秒** 和 **68.7 秒**，分别发出 17 次和 15 次模型请求；同一连接下一条不需要工具的问答只要 5.4 秒。慢的不是模型本身（单次请求多数 2–7 秒），而是一条天气题走了一长串串行步骤，其中有一个实打实的缺陷和三处放大耗时的设置：

1. **缺陷**：成员到达轮数上限后的"收尾总结"请求，在非 Codex 登录的连接（Anthropic、各种兼容接口）上必定失败，成员的全部工作只剩一句"本轮已停止"，主 Agent 只好再派一次。
2. 检索成员读网页时只保留最近一次读取的正文，长页面只能用偏移量一段段重读，6 轮用完还没写出答案。
3. 答案写出来之后还要再过两到三道核验，合计 13–24 秒。
4. 主 Agent 每次请求都带着 82 个工具的完整定义（约 4.6 万 token），尽管它在这类问题里只负责派单。

## 时间去哪了

### L1 · 缺陷：非 Codex 连接上，到上限后的收尾请求必定失败

`src/runtime/limitDelivery.js:16` 给收尾请求固定传 `functionTools: []`，但不传工具协议；`src/openai.js:1427` 的分发规则是"只要 `functionTools` 是数组且没有协议，就按 OpenAI Responses 发"。Codex 登录在这之前就分流了，所以不受影响；Anthropic 和兼容接口连接则把 Responses 格式的请求发到了自己的地址，0.3–0.4 秒返回错误，收尾退回宿主兜底文本。实测里两次运行的四个成员全部命中（Trace 里请求体的字段是 `include / input / instructions / store`）。隔离探针 `limit-delivery-routing-probe.mjs` 不联网也能复现分发结果。该写法 10-27 随 `006797b2` 引入，现有测试没有覆盖非 Codex 连接。主 Agent 自己的限额收尾走同一个函数、同样不带协议，按代码同样受影响，本轮实测只触发了成员侧。

代价：成员整段工作（第 1 次 44.0 s、第 2 次 28.3 s）没有形成报告，主 Agent 被迫再派一次；第二次派单加成员在两次实测里分别是 36.3 s 和 14.9 s。收尾若成功大概率不需要再派单，但收尾本身也要一到两次请求，净省多少没有实测。

### L2 · 成员读长页面只能翻页，6 轮用不完

成员每轮只保留最近一次工具结果的全文，更早的压到约 900 字（`src/agents/subAgent.js:420`，`keepRecentResults: 1`，这是我 11-04 为省 token 加的）；每次读页给模型约 8.4–9.0k 字。气象局页面前面全是导航，预报在九千多字之后；wttr.in 的 JSON 里明天的数据在一万两千字之后。于是成员用 `offset` 一段段重读，读到后面又忘了前面，6 轮（`shared/agent/taskEvaluation.js:11` 的 `initialRounds`）用完还没写出答案。主 Agent 派单时把问题扩成六七个字段再加交叉核对，也让成员多读了几页。仓库里有现成的天气快路（`fetchWeatherFastPath`，wttr.in 摘要），但它藏在 `web_search` 内部，成员直接读页时用不上。

### L3 · 答案写完后还有两到三道核验

主 Agent 写完答案后有一次完成检查（10.1 / 11.9 s）和一次不确定内容核验（2.7 / 1.8 s，`finalizeNode.js:29`）；成员交回前还有自己的完成检查（`subAgent.js:310`，第 1 次实测 11.2 s，并且它要求补查导致成员又跑了一轮）。完成检查慢主要因为要输出约 1 000–1 200 token 的逐项 JSON。纯问答那一条里，回答 2.0 s、检查 3.2 s，检查占了六成。核验确实拦过无依据内容（Codex 审计里的手机样本），不能直接删，但三道串行检查可以合并。

### L4 · 主 Agent 的请求过重

主 Agent 每次请求带 82 个工具定义（52 个 MCP 工具、文件、技能等，119k 字），输入约 4.8 万 token，其中 4.6 万是可缓存前缀。一轮天气题里主 Agent 的 3–4 次请求占了全部输入 token 的六成（159k / 263k）。缓存命中时首字约 1 秒（纯问答样本），冷启动第一请求 4.7–4.9 s。检索类问题里主 Agent 只派单，不需要这些定义。

### L5 · 其余

- 重复生成：成员写一遍报告（11.1 s），主 Agent 再写一遍答案（6.7–6.8 s）。
- 读页顺序：`fetch_url` 的自动模式先走 Jina、失败才直连（`fetchUrlTool.js:659` 起）；实测一次 Jina 花了 21.7 s，同站直连是 0.04–1.3 s。
- 思考强度：请求没有设置 `output_config.effort`，Opus 5.5 的派单、检查、核验都按默认强度思考。调低控制类请求的强度是候选项，但会影响判断质量，必须先有评测。

## 手机

没有新的手机记录（最近的设备备份停在 11-07，0.7.18 的运行没有导出），本轮没有真机实测。11-07 的天气样本（0.7.16，Codex 登录 `gpt-6-astra`）复算为 85.3 秒、9 次模型请求：派单 4.8 s，成员 49.2 s（模型 25.0 s，读页 23.9 s，其中一次 20 秒超时且串行挡住了另一条 1.4 秒的读取），写答案 7.0 s，检查 8.7 s，改写 7.0 s，再检查 5.9 s，核验 2.4 s。当前源码里串行读取（`ios/Melo/AgentLoop.swift:667`）、20 秒整页超时（`ios/Melo/WebPageTools.swift:29`）和正文不流式显示都还在。手机的收尾走自己的传输层，不受 L1 影响；L3 的多道核验两端相同。

## 与 Codex 11-09 审计的关系

Codex 的结构性结论成立：成本在多次串行模型请求，手机正文不流式、读取串行，完成检查范围宽。本轮补充的是它没有覆盖的部分：当前版本的实测（它引用的桌面样本是主 Agent 还能自己检索时的 5 次请求 / 35.7 秒，现在是 15–17 次 / 69–106 秒）、L1 的收尾缺陷、L2 的翻页循环、L4 的 82 个工具定义和 Jina 读页的 21.7 秒。

## 建议顺序（未实施，秒数待同一轮对照实测确认）

| 顺序 | 改动 | 预期大小 | 风险 |
| --- | --- | --- | --- |
| 1 | 修 L1：收尾请求按连接的真实协议发送，补非 Codex 连接的测试 | 大（非 Codex 连接） | 低，属于缺陷修复 |
| 2 | 单事实检索不再翻页：按体积而不是按条数压缩旧结果、读页返回正文而不是导航、天气等结构化来源一次取到、派单只写用户问的字段 | 大（成员占 55–71%） | 中，改动成员取证方式，要保住证据完整 |
| 3 | 三道核验合成一道，检查输出改短 | 中到大（13–24 s） | 中，不能放过无依据内容 |
| 4 | 主 Agent 请求瘦身：检索类回合只带派单工具和一行目录 | 中，费用降幅大 | 中，执行类任务仍需要完整工具 |
| 5 | 单成员、证据已核实时直接交付成员报告 | 中（约 7 s） | 中，主 Agent 的整合职责要保留审核 |
| 6 | 读页先直连或与 Jina 并发，Jina 设短超时 | 小到中，主要治偶发卡顿 | 低 |
| 7 | 手机：只读工具并行、整页超时缩短并换源、正文流式显示 | 见 Codex 审计 | 中 |

验收口径：同一问题、同一连接、改动前后在同一轮里各跑若干次，同时报告总时长、模型请求数、首段正文时间、token 与答案质量；质量没有评测集之前，结论只能写"未检查质量"。

## 边界与证据

- 链路：`chatRoutes` → `chatExecutionRunner` → `prepareNode` → `invokeModelNode`（派单 / 整合 / 检查）→ `internalMembers` → `subAgent` → `executor` / `fetchUrlTool` → `limitDelivery` → `finalizeNode`；手机为 `ChatStore` → `AgentLoop` → `WebPageTools`。停在供应商传输边界，不猜测供应商内部排队。
- 未覆盖：手机当前版本真机、Android、Codex 登录连接在当前桌面版上的表现、搜索工具本身（本轮成员没有调用 `web_search`）。只有三次实测，属于方向性结论，不是统计意义上的平均值。
- 证据在 `.tmp/latency-audit-20261110/`：三次探针的事件流与回复、三份时间线（`*-timeline.txt`）、分析脚本 `trace-timeline.py`、隔离探针及其输出。对应 Trace 在 `.tmp/melo-home-user/traces/` 下的 `fbcb01fd…`、`32af241b…`、`849910db…`。
