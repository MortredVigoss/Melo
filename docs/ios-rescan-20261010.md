## 复扫结论与实际修复

- 确认一项手机缺陷：61 条交替问答（30 轮完成对话 + 当前问题）使用 `suffix(60)` 后，从缺少对应问题的旧回答开头。回归在旧代码明确失败，日志为 `history-red.log`。新增 `ConversationHistory.recentTurns`，按最近连续用户轮次选择；当前轮不静默切断，仅影响发给模型的上下文，磁盘历史不改。ChatGPT、Chat Completions、Anthropic 三条请求均接入并断言实际请求体。
- 60 条是软条数上限，并非 token 预算；如最新一轮本身超过上限，仍保留整轮。桌面的 token 预算、自动摘要压缩尚未移植，不能将本修复写为长期记忆全部对齐。
- 手机目前同一时刻仅一轮发送，模型、连接、指令和历史在创建异步任务前捕获；无桌面 skill / Agent 工具委派路径。主线权限 requestId、空工具白名单、审批恢复修复属于桌面执行器；手机接力只提交请求，权限仍回到执行设备核对。没有将桌面工具执行能力冒称为手机本机能力。
- 手机失败后保留已保存的问题，显式“重新生成回复”不会重复追加问题；这是新的推理请求，不等同于桌面服务的同 requestId 结果回放，且目前没有同请求服务端去重。已验证中断、重启读回、手动取消、重试后仅一条问题和一条答案。
- 原生语音既有 60 秒时限、结束等待及草稿回收，相关测试通过；桌面新增网页原生桥丢消息超时路径不在 Swift 手机里复制一份。
- 旧消息缺日期问题位于桌面同步导出/排序；最新稳定日期兜底及幂等测试通过，手机外来格式校验继续保持。实际远端同步部署与真实两端联调本轮未验。
- 设计 Melo 与 melo ui 没有新实现。共享神经 renderer 与已装 0.5.10 源码/打包 manifest 一致，任务空间分页与语音设置桥仍通过；本轮不另做视觉改版，也不把几何测试当作真机帧率验收。
