## 发现与复现

### 1. 同一失败会消耗全部轮次（设计缺口）

主循环没有按“工具 + 参数 + 错误 + 有无进展”判断是否重复。隔离真实执行图让模型每轮用新 call ID 请求相同参数，工具每次返回同一永久错误，得到 **10 次模型请求、10 次工具失败**，然后才停止。原生协议已拦截重复 call ID，但新 ID 的同义重试没有拦截。子 Agent 和技能同样会跑满各自的 20 / 16 次测试上限。

这不是无限循环，但会浪费时间和用量。主对话也没有贯穿模型、工具、委派和整理阶段的统一累计时限/用量上限；次数有限不等于等待短。

### 2. 工具插件回调在超时和取消保护之外（条件性卡死）

`src/tools/executor.js:127` 在创建取消控制器/计时器之前等待 `tool:before`；`:194,220` 先清理计时器再等待 `tool:after`，错误路径 `:230` 也直接等待。底层 `src/plugins/hooks.js:127` 对回调没有截止时间或取消竞速。

实测设置工具 timeout=15ms，回调进入后发送 abort，60ms 后执行 Promise 仍未完成；只有人为释放夹具回调才退出。after 回调还出现取消后最终返回 ok=true。若回调永不返回，会一直悬挂；同聊天串行队列等待真实执行结束，因此后续消息也可能排队。

**触发边界：** 当前源码未发现生产启动时自动注册这些插件回调，只发现注册 API 与测试使用；这证明扩展点不可靠，不代表用户现在已启用了故障插件。

### 3. 卡住的底层执行会持续占用工作区（恢复缺口）

`src/agents/delegate.js:32` 的 Promise.race 允许成员超时返回；`src/agents/workspaceScheduling.js:13–18` 保留工作区租约，等待底层工作以及 pending 工具真实结束。保护写入不重叠是正确的，但没有独立的卡住状态、终止/隔离和恢复流程。

实测第一成员忽略取消、一直等夹具；20ms 超时后返回 cancelled。第二个同工作区写成员在 30ms 后也超时，实际启动次数 **0**；仅释放第一底层执行后第三成员才能启动。永久不结束则后续同工作区写成员持续受阻。正常 bash 取消会杀进程组，现有回归通过；这里针对不遵守取消的扩展/异步实现，不能把所有工具都说成会卡死。

修正时不能简单到点释放写锁，否则旧写入仍可能与新成员并发。应先终止可终止执行；无法证明已停止时隔离该工作区并明确返回 blocked，给出安全恢复入口。

### 4. 团队最终总结绕过总时限（确定漏洞）

`src/agents/team.js:126` 在成员执行后清理团队计时器，`:129` 才发总结请求，而且使用原始 signal。团队成员还剩时间时进入总结，总结不再受剩余团队时间约束。

用生产团队函数和虚拟时钟，配置总时间 60 秒，推进到 61 秒时总结仍等待、signal 未取消；释放后返回 ok=true、budgetExceeded=false。真实请求仍受供应商单次默认 10 分钟超时约束，所以不是无限网络请求，但会违反团队总时限。

## 建议修复顺序

1. 用一个运行范围携带绝对 deadline、累计工具/模型用量和取消状态；覆盖模型、工具、hooks、子成员、技能、团队总结与保存收尾。子任务只能使用父任务剩余额度。
2. 同一永久错误重复 2–3 次且没有进展时停止；参数错误/权限拒绝不盲目重试。瞬时故障采用有次数上限的退避，修正参数后允许合理重试。
3. hook 回调加独立上限和取消处理；取消后的结果不得再记成功。必须保留不再执行副作用的检查。
4. 卡住写任务保留隔离保护，明确反馈阻塞原因，支持终止/确认清理；排队取消及时返回，不能悄悄无限等锁。团队计时器覆盖总结阶段。
5. 手机沿用同一失败分类和重复判断规则，保留现有 6 轮上限；单独验收系统授权等待与用户停止，不把桌面验证当手机实测。
