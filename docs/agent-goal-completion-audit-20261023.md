# Agent 目标保持与结束条件审计（2026-10-23）

范围：基于 `da86326` 检查桌面主聊天、委派/技能、iPhone 及 Android 共享循环。用户要求先审计、出方案；本轮仅补文档与本地隔离回放，没有修改产品代码、配置、账号或数据，没有安装、推送或运行 `git pp`。

触发案例：用户问“下周演唱会天气”，Agent 查日历找到演出后，询问用户场馆地址并结束；用户再次要求搜索才完成。审计目标是通用的任务完成闭环，不为演唱会写专用流程。

## 1. 三个问题的结论

| 用户问题 | 当前结论 | 实际边界 |
| --- | --- | --- |
| 用户目标有没有保存？ | **原始消息有保存；本轮也持有原始问题。** | 没有独立、持续更新的目标状态，不能区分最终交付、已知事实、待补步骤、真正需要用户回答的问题。 |
| 工具返回后能否继续调用其他工具？ | **可以，且生产路径回放验证了多轮工具调用。** | 继续与否主要取决于模型下一次是否发工具调用；它一旦改成普通文字，Host 通常就结束这一轮。 |
| 最终回复是否验证任务完成？ | **有证据回执和部分校验，没有完整的目标覆盖检查与续跑闭环。** | 回执在循环结束后生成；`partial/blocked` 不会反馈给循环。已读相关来源也不等于回答了最终问题。 |

因此，不应把问题归因为“每轮只能用一个工具”，也不宜仅通过增加最大轮数或改一句提示词处理。需要补的是：**保留可验收目标 → 工具证据更新进度 → 检查候选回复 → 需要时有界继续执行**。

## 2. 源码证据

以下行号对应审计基准；后续以函数名定位。

### 2.1 原始目标保留，但不是执行状态

- 桌面 [sendChatMessage.js](../src/services/chat/sendChatMessage.js) 254–271、321–345：原文存入 user message，通过原子更新保存；365 附近传递 `latestUserMessage`。
- iPhone [ChatStore.swift](../ios/Melo/ChatStore.swift) 361、409–418：保存用户问题；[ChatGPTAccount.swift](../ios/Melo/ChatGPTAccount.swift) 229 和 [Network.swift](../ios/Melo/Network.swift) 163：从原始请求历史传入本轮问题。
- [shared/agent/turn.js](../shared/agent/turn.js) `startTurn`：跟踪调用、轮数、预算、重复错误、必用工具，但没有最终交付要求、未完成项和已核实事实。
- [shared/agent/execution.js](../shared/agent/execution.js) `executionScene` 保存有界 `query`、执行事件与最终回执，用于历史与显示。它不是持续驱动执行的目标记录。
- [shared/agent/search.js](../shared/agent/search.js) `continuedRequest` 会从最近用户消息恢复显式“继续/重试”的检索请求；这有助于追问，不等于任意补充都能更新一个持久的任务目标。

**不能声称目标原文丢了。** 缺的是原文之外的执行约束：查到“演唱会”只是中间事实，用户要求的“天气”仍未交付。

### 2.2 多轮调用存在；停止点没有目标检查

| 路径 | 继续调用 | 收尾条件 |
| --- | --- | --- |
| 桌面主聊天 | 工具结果回填模型历史，下一轮仍提供工具 | [invokeModelNode.js](../src/services/chat/execution/invokeModelNode.js) 287–302：无工具调用就 `complete`，随后 `break` |
| iPhone API / ChatGPT | [AgentLoop.swift](../ios/Melo/AgentLoop.swift) 315：追加整轮工具结果，继续循环 | 247–252：无工具调用就 `complete` 并返回 `.answered` |
| 委派成员 | 成员自己的工具循环与预算 | [subAgent.js](../src/agents/subAgent.js) 240–244：同样结束 |
| 技能 | 技能自己的工具循环与预算 | [skillExecutor.js](../src/agents/skillExecutor.js) 286–292：同样结束 |
| Android | 工具结果按协议追加到历史，再请求模型 | [SharedChatAgent.kt](../android/app/src/main/java/com/melo/android/chat/SharedChatAgent.kt) 173–179：同样结束；本轮只静态核对 |

补充边界：

- 共享 `complete` 会检查已发出的工具是否都返回、`requiredTools` 是否成功；它不检查每项用户要求。桌面某些搜索路径可以因此拦下没有搜索的回复，但仍停止而非补做。
- iPhone `PhoneCoreTurn` 目前只接工具名和轮数上限，没有接入桌面那套 `requiredTools/toolDependencies`。ChatGPT 路径另有“是否实际搜索/打开过网页”的校验，失败时抛错，不续跑；API 路径不能假定有相同校验。
- [ChatGPTAccount.swift](../ios/Melo/ChatGPTAccount.swift) `CodexResponsesTransport.round` 保留后续轮次的工具列表，只把首轮强制搜索的 `tool_choice` 恢复成 `auto`；不存在普遍的“第一工具执行后工具就被收走”。
- 搜索与设备权限仍会影响某个实际请求能否继续。没有那次完整 trace，不能断言它当时提供了哪个工具、采用哪种连接方式，或排除权限与路由的影响。

### 2.3 完成回执是后置记录，不是目标控制器

- 桌面循环退出后才把 `completionForReply` 交给 [finalizeNode.js](../src/services/chat/execution/finalizeNode.js) 136。iPhone `AgentLoop.run` 154–159 在 `invokeModel → validate → finalize` 后生成回执。Android `finish` 也是生成回执后返回。
- [completion.js](../shared/agent/completion.js) 28–56：普通回答有非空文字即可交付；研究任务要求已读、词语相关、最终引用的来源；操作要求独立终态证据。**没有逐项核对最终答案是否包含用户所要的结果。**
- 原有不确定性验证仅在有不确定标记且符合分类条件时运行，主要核实某条说法，不检查遗漏的子任务，也不恢复工具循环。
- 委派/技能的 `ok` 主要表示成员在预算内返回；[handoff.js](../src/agents/handoff.js) 和团队编排保留回执，但不会把“成员返回了”自动提升成有证据的父任务完成判断。

这与 [此前完成回执的边界](completion-receipts-20261020.md) 一致：当时实现的是诚实展示执行与证据状态，并未实施通用的自动补做机制。

### 2.4 在接续跑之前，必须修正证据分类

已确认两处会影响新机制的基础问题：

1. `completionKind` 的只读工具列表没有 `calendar_list_events` 等设备读取工具。iPhone 工具定义明确 `writes: false`，完成分类却会判为 action，要求本不适用的外部操作终态。受控回放里，日历 + 天气网页 + 天气回答仍得 `research-action / partial`。
2. iPhone 对 Hosted Search 主要记“搜索成功”工具标志；`completionObservation` 目前只为特定网页/搜索适配器提取正文来源，日历输出也没有转成可供目标检查的结构化事实。不同入口提供的证据形状不完整一致。

**不能简单写成“回执不是 completed 就再调用模型”。** 否则真实完成但证据不被识别的任务会反复执行；发送消息、写文件等副作用尤其不能因总任务未完成就重放。

## 4. 建议实施方案

沿用现有共享 Core、执行记录、预算与权限系统，增加一个小的目标状态及结束前决策入口；不另建大型工作流框架。

### P1：目标与证据契约

- 为需要工具/多步交付的任务增加版本化目标状态：原始消息引用、当前目标与约束、交付要求、已知事实及证据 ID、未完成项、待澄清项。原始消息是依据；补充要求形成新版本，不能被工具正文或模型摘要改写授权范围。
- 每次工具结果后更新事实；只保存必要的有界信息，原始敏感内容仍按既有存储策略处理。跨轮继续从已完成步骤接续，新话题不能误接旧任务；旧记录无目标状态时兼容读取，不伪造完成证据。
- 工具目录统一声明读/写/外部操作性质，替代零散名称正则；手机日历、网页、Hosted Search、MCP、成员交接统一转换成带来源的 observation。搜索摘要、已读正文、设备事实与操作回执保持区别。
- 对时间相关任务记录绝对日期、时区、地点、资料时间/适用范围。天气超过可用预报范围时，允许给出有根据的限制说明，不编造，也不要求不断搜索。

### P2：结束前检查与有界继续

将“无工具调用”视为候选回复。在调用共享 Core 的 `complete` **之前**运行统一 `assessCompletion`：

| 决策 | 行为 |
| --- | --- |
| complete | 交付要求得到回答，关键事实有相应证据；允许结束 |
| continue | 仍缺结果，且有获准、可执行的下一步；将具体缺口反馈给模型继续 |
| needs_user | 真正存在无法自行消除的歧义、必须由用户决定的事项或权限要求；提出一个明确问题 |
| blocked / partial | 供应商不可用、合法证据无法取得或现有能力不支持；交付已有结果和具体缺口 |
| cancelled / budget_exhausted | 立即停止，保留进度 |

- 目标拆解尽量随正常模型轮次生成，不单独为每条普通聊天新增规划请求。规则先检查证据 ID、必需项、来源、权限与缺口；复杂语义在候选结束时才做有界检查。模型的“我完成了”不能当 Host 证明。
- 普通聊天、翻译、创作保留轻量路径，不因没有工具回执反复核实。检测“问题是否回答”与核实“每句话绝对正确”分开。
- 建议默认最多 **2 次自动纠偏**，计入原有总轮数、时间、token、工具次数和成员预算；不新增一套可绕开的预算。重复错误、无进展、取消机制继续有效。
- 复用共享 Core 的 `feedback` 转移，保留本轮工具历史，继续同一个执行上下文；不重新发送整条用户消息来重启任务。已完成写入/发送的操作禁止因纠偏重复执行。
- 公开搜索可找到的缺失信息，优先在授权能力内补查；多个合理匹配仍不能消除歧义时再问用户。对外搜索只发送必要的公开事件线索，不上传完整私人日历。

### P3：所有入口接同一个决策，补齐显示

- 桌面主聊天、subAgent、skillExecutor、iPhone API/ChatGPT、Android 共用目标与停止规则，平台适配器只负责模型传输、设备事实和授权。
- 团队交接区分“成员结束”和“子任务交付”；父任务依据各交付要求汇总，不能用任意成员的 `ok` 或自报 approve 代替整体完成。
- 在现有执行面板显示“正在补查什么 / 已完成什么 / 等待用户什么 / 为什么停止”，保存目标版本、缺口、决策原因及证据引用。候选回复在完成检查前不能当最终答案持久化或朗读。
- 不自动增加权限；工具、skill、委派的能力交集与原有审批都保留。账号、聊天和原图格式兼容，旧数据无需清空重建。

### P4：验收与交付

先把下表接入共享 fixtures 和生产调用路径的测试，证明修复前失败、修复后通过；再按完整改动文件执行测试计划、组合日常与原生验证。共享 Core 变动按现有规则扩大检查，不能只跑新测试。

| 验收场景 | 必须证明的行为 |
| --- | --- |
| 日历缺场馆、公开检索可以找到 | 首次请求内继续找场馆、查对应日期天气并回答，不要求用户再次催促 |
| 日历已有地点 | 跳过不必要的场馆搜索，直接获取天气；不能套固定工具顺序 |
| 模型提前追问可查的信息 | 被结束检查拦下；下一次确有工具执行，最终交付有天气依据 |
| 模型直接正常串联工具 | 不追加多余纠偏或复核调用 |
| 搜索成功但只有演出页面、没有天气 | 不能标成天气任务完成；存在下一步则继续 |
| 日期超出预报范围 | 诚实说明时间范围和已查证信息，合理终止，不无穷搜索 |
| 同名演出/多个城市 | 用现有事实排除歧义；仍不唯一才 needs_user |
| 无联网权限、服务故障、授权拒绝 | 不越权、不假装完成；明确缺口并有界停止 |
| 日历读取与 Hosted Search 的完整回答 | 不误判为未验证外部操作，已有合格证据不重复查询 |
| 连续错误、无进展、预算、用户停止 | 模型与工具计数受限，停止后零新副作用 |
| 用户中途改日期、回复地点、稍后“继续” | 保持目标关系，更新对应约束；切换话题不串任务 |
| 子任务已写入/发送但总任务未完成 | 只补缺项，副作用执行计数保持 1 |
| 普通问答 / 用户明确只要一句话 | 保持直接回答，不引入每轮强制工具或 Judge |
| 三协议与跨平台 | Responses、Chat Completions、Anthropic 的结果回填和续跑一致；共享 fixtures 在 Node/JSCore/Android 执行，设备端另实测 |

最终真机用可控测试日历事件验收多步链路和取消，明确区分合成模型、真实服务与实体设备证据。若能定位原始故障轮次，再做脱敏回放，核实该次是否还叠加了路由、权限或供应商问题。

建议顺序：**先把验收反例固定 → P1 目标/证据 → P2 有界闭环 → P3 全入口接线 → P4 组合验收**。当前为待实施方案。
