# Melo 图片预览、存储与承载能力治理计划

日期：2026-10-15（Australia/Melbourne）。用户确认报错发生在电脑端。本轮完成只读调查和方案，不改产品实现，不消费模型额度，不重启/安装、不清理用户文件。

## 1. 已确认的结论

当前报错首先是**图片访问地址生命周期缺陷**，不能按“图片损坏”或“缓存太多”处理。

1. 在运行中的桌面 Melo 点击“生成图片”预览，显示“图片无法载入，文件可能已过期或不可用。”，随后关闭并恢复聊天焦点。
2. 图片文件存在：2,090,093 字节，1289×1221 PNG，SHA-256 `14c41bb4539b40e9a722e2aca1662b952575855bb6fc54b33ccacb9e0ed2c03a`。
3. 聊天附件的旧签名地址已过期，GET 返回 **403**；同一个文件通过任务回看重新签发后 GET **200**，HTTP 返回字节 SHA 与磁盘一致。
4. `src/web/urlSigning.js` 默认有效期10分钟，最高1小时，签名密钥每次服务启动重建。`desktop-ui/imagePreview.js` 直接复用缩略图 src；`executionScenes.js` 按已存 path 更新签名。聊天预览没有同等恢复路径。

证据：`.tmp/image-capacity-audit-20261015/signed-url-status.json`（已省略签名查询参数）；源码散列：`source-manifest.json`。当前运行服务为 PID7966，健康回执 home 为 `.tmp/melo-home-user`，启动修订 `b662c627f127` 且dirty；本次源码快照 HEAD 为 `dece2b5`。运行时旧模块与共享当前源码须分别验收，不能靠更新磁盘源码假定运行实例已修复。

**承载能力结论：当前约2MB图片的失败已由失效地址解释；尚无证据证明是容量不足。** 当前检查是静态源码与小样本，不足以给出“最多支持几万张、多少并发”的可靠上限，需要独立压测。

## 2. 当前结构与薄弱点

| 范围 | 已核对事实 | 风险 / 要补的能力 |
| --- | --- | --- |
| 原图访问 | 成图在工作区 `generated/`，历史正文/附件保留短期签名 URL；任务 sidecar 可按 path 重签 | 历史聊天、预览、下载入口不一致；重启/换端口/过期后不能把旧地址当永久引用 |
| 资源写入 | 通用 `imageArtifacts` 将图转PNG后直接writeFile；Codex另有直接写文件路径 | 多实现缺共用提交/校验状态；取消或消息绑定失败的孤儿文件、磁盘满及中断需恢复，不把所有路径一概称已有原子写入 |
| 原件保真 | 桌面已保存文件可下载同字节；通用保存会转PNG；手机store先解码，最长边默认4096，再编码PNG/JPEG | “下载与本地文件一致”不等于“与供应商原始字节一致”。原件、展示版、编辑输入必须区分；已有手机图片不得伪称可恢复丢失的高分辨率 |
| 缩略图 / 预览 | 桌面聊天直接用附件 URL 原图，无专用图片磁盘缩略图层；手机已有512缩略解码，预览默认4096 | 桌面列表大量原图解码；手机单View持有缩略图，尚无统一带字节预算的去重/LRU队列；内存压力、关闭、滚出可见区需可验证释放 |
| 下载 | 桌面fetch整图→Blob→FileReader Base64→WK bridge→Data→NSImage校验→原子写出 | 64MB检查发生在Blob构建之后；完整Base64和原生解码增加峰值内存，适合改为受控流式原件复制 |
| 字节 / 像素限制 | 桌面上传20MB、图片工具20MB、保存下载64MB；部分Sharp路径限8000万像素；Codex读SSE未见统一事件/总字节上限；手机原图/参考24MB、结果Base6432MB、索引16MB | 分散限制不能代表统一容量；压缩小、像素大也会造成内存峰值；部分路径限像素不等于所有路径安全；需在全量分配前预检与流式计数 |
| 生成中预览 | imageTask每帧另存 `preview-UUID.png` 到成品同目录，场景只保留每operation当前预览 | 旧预览/失败临时文件可能成为无索引文件；需生命周期记录与回收，不能按前缀直接批删 |
| 缓存 | media-cache是提取结果JSON；单项2MiB、TTL7天、预算256MiB，写入触发且最多每小时清扫 | 这不是原图/缩略图缓存；预算是清扫后的目标，非每次写入硬上限。清此缓存不能修403预览 |
| 存储统计 | inventory只扫描MELO_HOME；生成图片位于仓库根 `generated/`，在本次home之外；`search.sqlite`被归类cache | 统计缺工作区图；SQLite同时含事实/用户编辑/使用记录，不能整库自动清除。现inventory仅report-only，未观察到因此删库 |
| 删除 / 备份 | 桌面删除聊天清提醒/运行账本/记忆来源，未见桌面图片共用引用回收；手机有引用链保护与待删除队列；可迁移JSON明确不含原附件 | 需要跨聊天、项目、草稿、编辑链的引用登记，以及含原图备份。聊天删除不能递归删共享工作区或原件 |
| 软件整体承载 | 状态按home常驻，冷启动仍读历史；bootstrap仍组装整体状态；桌面输入可data URI存checkpoint | 多图历史会放大JSON、网络传输、内存快照和重绘成本；需附件外置、摘要传输、分页/可见区加载，保留聊天/记忆语义 |

本机只读快照：home约 **7.00GiB**（模型约 **6.46GiB**）；根generated目录 **20文件/23.49MiB**，其中4个preview前缀文件，包含测试产物，不视为20张用户成品。该目录之外的所有项目工作区尚未全盘盘点。文件系统可用约190GiB，不是本次失败的磁盘不足证据。原生壳约37MiB、Node约200MiB为单次空闲RSS，**不含完整WebKit进程树，也不是峰值承载证明**。

证据：`.tmp/image-capacity-audit-20261015/storage-snapshot.json`。其中Sharp配置来自独立调查进程，不代表运行服务器设置。

## 3. 目标结构

```text
聊天 / 项目 / 草稿 / 编辑链 / 任务记录
                   ↓ 只保存稳定 assetId 与版本
             原件登记 + 引用关系 + 状态
                   ↓
           原件文件（用户成果，长期保留）
                   ├→ 缩略图（可重建、带磁盘预算）
                   ├→ 显示预览（可重建、按屏幕解码）
                   ├→ 编辑输入副本（明确变换，不替代原件）
                   └→ 原件导出 / 备份

生成流 → staging临时文件 → 校验与原子发布 → 引用提交
           ↓取消/失败             ↓待绑定 / 绑定成功
     有期限临时清理         启动恢复与孤儿隔离

访问入口 → 校验所属home/工作区/引用 → 临时签名或本机流
```

原件登记至少包含assetId、home/工作区归属、相对位置、内容SHA、字节数、MIME/像素/方向、状态、创建时间、来源与引用；没有必要为此引入第二套业务事实库。优先在现有持久化体系内加资源表/提交日志，文件与数据库用可恢复协议协调，不宣称跨文件系统与数据库天然事务。

缓存可丢弃，原图和用户成果默认保留；缓存命中与失效不能改变聊天历史或触发付费生图。资源登记和多端同步协议是不同边界，本轮不顺带启动图片二进制跨端同步。

## 4. 实施顺序与验收

| 阶段 | 要做的事 | 交付 / 验收 |
| --- | --- | --- |
| **P0：修桌面预览与下载** | 从已可信登记的附件/任务artifact path定位资源，在呈现/点击时刷新签名；预览、聊天图、下载、任务回看共用解析入口；区分地址过期/文件缺失/文件损坏/不支持。旧签名p参数只能作为候选，不能仅decode后给任意路径重签 | 旧图片无需重生成可开/可下载；超过10分钟、重启、换端口、重开聊天均成功；403最多一次受控解析刷新，404不盲重试；原件SHA不变；跨home、越界/软链接路径拒绝 |
| **P1：建立完整资源台账与容量基线** | 枚举已登记home与项目工作区，不扫整台磁盘；核对消息/任务/草稿引用和实际文件；统计原件、衍生图、预览、提取JSON、模型、日志和独立记忆数据；打点每次下载/解码/保存/传输耗时及字节 | 可解释缺文件、旧URL、重复内容和无引用文件；统计注明覆盖范围/截断；不直接删除。记录Node heap/RSS/external、整个WebKit进程树、手机footprint和磁盘写入 |
| **P2：统一原件保存与恢复** | 统一生成/编辑/上传的asset登记；完整原始数据保留，展示转码另存；staging→校验→原子改名→提交引用，未绑定资产保留待修复状态；取消/失败/进程中断可恢复 | ENOSPC、权限错误、写入/绑定失败、各提交阶段强杀可重复恢复；不会将半文件标成成品，不丢已生成结果，不覆盖原件；含图片备份/恢复验证。桌面先行，手机后做兼容扩展 |
| **P3：缩略图与内存缓存** | 列表使用缩略图，预览按屏幕像素解码，100%查看按需；请求去重、可取消队列、内存LRU按解码字节计费；关闭/切图/后台释放；下载原件从验证资源流式复制，减少Base64桥接 | 多次打开同图复用；连续切50张和开关100次不线性增长；低内存可降级，界面仍能聊天；导出SHA等于原件；压缩尺寸小但高像素的图不会无限分配 |
| **P4：磁盘缓存与安全回收** | 原件/衍生/生成中预览分区；缓存设置独立预算/TTL/LRU；引用覆盖聊天、项目、草稿、任务与编辑链；孤儿先隔离，清理只操作可重建资源或明确授权的原件；恢复队列持久化 | 清缓存后原图/聊天/记忆/凭证不变且可重建；共享原图不被单聊天删除带走；清扫与生成/预览/删除并发一致；低磁盘先暂停新写入并保留已有成果 |
| **P5：大历史与批量承载** | 将大data URI迁到assets，正文保留引用；聊天/图库分页、可见区加载；缩小bootstrap/任务响应；统一解码/SSE/下载输入预算与重型任务排队；保留home隔离与取消语义 | 100/1000/10000资源登记分层基准；100个对话、多图历史、1/2/4并发队列测峰值与P95；取消/后台不会继续解码整批。先确认边界，不直接放开4路真实生成 |
| **P6：产品接入与双端验收** | 数据页显示准确容量、原件/缓存差异、清理结果与错误；迁移有备份、旧格式兼容和回退方案；验证设计线程新语言层兼容、手机独立预览/保存/文件权限 | 定向回归→UI/iOS专项→完整发布gate；之后签名/保数据覆盖与实际原生操作。模拟器、实体设备、真实服务分别记录，真实生成额度另按用户授权 |

P0可以独立交付，不等待其余架构改造。随后P1给P2–P5实测基线，P2稳定资产事实后再依赖它做缓存和回收，防止先清理后发现丢图。每阶段单独提交、更新总览与证据，不混合并行语言/模型/OAuth WIP。

## 5. 初始预算建议（待基线验证后固定）

这些是建议初始策略，**尚未实施，也不是当前支持承诺**；先保持已公布输入边界，调整需有测试和明确UI说明。

| 资源 | 桌面建议起点 | 手机建议起点 |
| --- | --- | --- |
| 原件大小 | 先兼容上传20MiB/导出64MiB等既有入口；统一限额前逐入口核对，不将64MiB导出误作64MiB上传支持 | 保留单图及参考合计24MiB现有限制；更大原件另评估，不直接放宽 |
| 列表缩略图 | 256/512/1024长边，按实际CSS尺寸/DPR选择；可见区加少量预取 | 256/512长边，按视图尺寸/屏幕scale选择；复用现ImageIO下采样 |
| 普通预览 | 2048长边起步，原始100%按需取原件/更细分视图 | 2048长边起步；4096只在明确需要且预算足够时，原件仍单独保留 |
| 解码缓存 | 128MiB目标上限，不含当前工作图/临时编码缓冲 | 64MiB目标上限，内存警告清衍生缓存；当前工作图也纳入总footprint观测 |
| 磁盘衍生缓存 | 512MiB目标预算，后台受控淘汰，可重建 | 128MiB目标预算，后台/系统压力可丢弃 |
| 重型处理队列 | 同时1个解码/转码起步，测过后可2；网络等待与重型解码分开 | 重型解码1个；列表预取可取消，不为每个View无限派detached任务 |
| 临时文件 | 生成中的每次任务独立目录；结束即处理，崩溃遗留24小时扫描；保留用户可恢复成果 | 同语义，但锁屏/保护数据未可用时推迟，不当成文件损坏 |
| 低磁盘 | 以预计临时/原件/衍生峰值及安全余量预检；不足则可解释失败，不动已有原件 | 同上，并处理系统写失败；不以固定“张数”控制 |

缓存预算是可重建数据预算，不能限制用户原件总量后自动删除。手机索引16MiB上限、大JSON和冷启动需在P5升级分页/增量策略，不悄悄把旧数据拒之门外。

内存计算例：4096×4096的4字节RGBA约64MiB；8000万像素约305MiB，尚未加压缩buffer、Base64、编码输出、GPU纹理等。图片文件只有几MiB不代表解码只占几MiB；Base64长度约原字节4/3，不同JS/桥接还可能持有额外副本。多图容量应按像素、同时处理数量和峰值测，不按PNG文件大小猜。

技术依据：Apple建议通过ImageIO下采样避免先完整解码再缩小，[iOS Memory Deep Dive](https://developer.apple.com/videos/play/wwdc2018/416/)；Sharp的[缓存与并发接口](https://sharp.pixelplumbing.com/api-utility/)可控libvips operation cache及每图线程数，但不是全应用RSS上限；[输入像素限制](https://sharp.pixelplumbing.com/api-constructor/)应与字节/队列预算并用。

## 6. 必做回归与压测矩阵

| 类别 | 覆盖内容 | 通过标准 |
| --- | --- | --- |
| 本次回归 | 新成图、10分钟后、进程重启、旧聊天、旧任务、原图下载、旧端口 | 正确恢复访问；不发模型请求、不改变原件；失效权限不被放宽 |
| 异常图 | 空/截断/错误MIME、大小上下边界、高压缩大像素、PNG/JPEG/WebP/HEIC及动图 | 以真实格式/像素/字节判断，支持差异清楚；不挂界面，不误称已保存 |
| 生命周期 | 生成预览→成品、失败、取消、编辑链、同图复用、删除聊天、未保存草稿 | 只回收无保护引用的临时资源；已保存结果不丢；迟到回调不更新已关闭View |
| 持久化恢复 | staging/发布/登记/消息绑定各阶段故障注入、索引损坏、ENOSPC、权限失败 | 可恢复日志与状态，无半成品成功回执；备份校验通过；回退不清理新数据 |
| 缓存 | TTL、按字节LRU、并发命中/淘汰、软链接与跨home、清缓存重建 | 原件/记忆/凭证不动；容量收敛到预算；临时超出有可观测时间界限 |
| 历史规模 | 100/1000/10000登记；多图长聊、大Base64旧checkpoint、多项目工作区 | 记录启动、bootstrap、列表、首张图P50/P95及峰值；图库不一次装全部原件 |
| 热使用 | 连续开关100次、50图切换、1/2/4任务排队、取消/后台恢复 | 关闭后不线性保留工作图；队列上限有效；聊天/设置仍可操作 |
| 原生交付 | WKWebView实际显示/缩放/导出；手机文件/照片允许与拒绝、后台/锁屏 | 原件导出SHA一致；用户数据前后相等；不要拿浏览器fixture代替原生 |

建议候选SLO：同机/同数据集暖缩略图P95≤200ms、普通预览P95≤1s；100次开关后的相关进程内存应形成稳定平台，去除缓存允许驻留后不得持续线性增长。基线先测WebKit/Node独立峰值及设备情况，未满足时记录瓶颈和重新定预算，不能先声称达标。

1万项基准可用元数据与有界实体图集组合，报告真实唯一文件/像素/总字节，不制造“1万张都解码过”的假负载。临时测试目录有硬磁盘预算与结束清理，不复制用户真实图片或生成收费样本来凑数。

既有 `imagePreview.browser.test.js` 使用永久 `/original.png` fixture，未覆盖签名过期/服务重启。本轮源码又接入设计线程i18n，旧fixture路由只显式提供imagePreview/styles；实施前须让新依赖被正常服务并收集pageerror，避免夹具超时掩盖实际问题。本轮未覆盖旧证据截图、未重跑该fixture。

## 8. 与项目边界重构的依赖（2026-10-15 补充）

见[项目边界核对与重构计划](project-architecture-plan-20261015.md)。项目配置、设备工作区与图片原件需分别定义生命周期：原件由稳定 assetId 及引用登记维护，聊天换项目只改变关联，不能据此移动/删除文件或重新生成图片。无项目聊天建议按需分配持久工作目录；操作系统临时目录只存可丢弃中间件。旧 generated/ 先登记、保留读取兼容，不随 APP_ROOT 默认回退的修复直接搬迁。
